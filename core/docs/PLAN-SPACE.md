# 占用与通行设计稿：碰撞的离散版，只认整数格和位掩码

> 状态：**设计稿，未实施**（2026-09-19）。上游 `PLAN-CORE.md` 第五节底层清单 **#5 空间**。
> 与 `PLAN-CLOCK` / `PLAN-ENTITY` / `PLAN-POOL` 同属 **L1 机制层**（分层规则见 `PLAN-CORE` 第四节）。
>
> 写给一段时间没看项目的人：**先读一、二两节就够决定**。
>
> **一句话**：它是全游戏所有空间动作的「能不能」总闸，
> 而它**不知道什么是床、什么是船、什么是田**。

---

## 一、要解决什么

后端不做物理（`docs/DECISIONS` D74：不许有速度和碰撞）。但**必须有人回答这些问题**：

| 问题 | 谁在问 |
|---|---|
| NPC 能不能走到码头 | 日程、处境时间线 |
| 这一格上站着 / 放着什么 | 建造、对话、拾取 |
| 这张床能不能摆在这 | `07` §四 主家装修 |
| 船往这边扩一格之后，船体还连不连通 | `07` §四 空艇网格建造 |
| 这格是崖缘 / 水面 / 漫滩吗 | 一切移动与放置 |

D74 挡掉的是**连续物理**（速度积分、碰撞响应、刚体）。它没有挡掉、也不该挡掉
**整数格上的占用与通行判定**——那不是物理，是规则，而且**进存档、影响重放**（判据一）。

⚠️ 如果不把它提成一个系统，会出两件事：

1. 它会被散进各个业务系统，每家写一份「能不能放」，**规则分叉**。
2. 有人按字面理解 D74，把判定塞给前端——**于是玩家摆得出后端不认的布局，存档一读回来东西全没了**
   （`PLAN-CORE` §7.4 的 C1 / C3 讲的就是这个）。

## 二、需要拍板的口径（有默认值，可直接说「按默认」）

| # | 问题 | 默认 | 说明 |
|---|---|---|---|
| a | 占用是不是独立状态 | **不是**。占用表是 `Placement` 的**倒排索引**，派生品，**不进存档**，加载后重建 | 权威是实体自己的 `Placement`。两份真相必然分叉；沿用 `PLAN-ENTITY` §3.5 的通则 |
| b | 占用表覆盖多大范围 | **只覆盖「活动区」**：玩家所在的局部网格地点 + 当前岛屿网格。进入时建，离开时丢 | 8000 个岛群的全量格表是不可能的，也没必要——没人看的地方不需要倒排 |
| c | 通行方式怎么表示 | **`uint32` 位掩码**，L1 只做位与。哪一位是「步行」「载货」「船」由 L2 定义 | 一旦 L1 出现具名的移动方式，它就认识业务了（`PLAN-CORE` §4.3） |
| d | 静态地形的通行位从哪来 | **slice 预烘焙**（由 generator 的 `landcover` / 坡度 / `water` 算出），不进存档 | 地形不变，烘焙一次即可；`terrain.npz` 已有全部输入 |
| e | `can_place` 的分工 | **L1 只给事实**（越界 / 不可通行 / 占用冲突 / 足迹越界）；**L2 合成裁决** | 「床要靠墙」「村址不落崖缘」是业务规则。**这也是两条轴的教科书例子**：最终裁决在 core 里（轴一 core 侧），但在 L2（轴二业务侧） |
| f | 足迹 | **业务给一组格偏移**；L1 按 `facing` 做整数旋转后求交 | 一张床占 1×2，一间仓占 3×3。旋转是纯整数运算，属 L1 |
| g | 同格能不能叠放 | **按占用等级**：阻挡 / 可叠 / 不占。等级是整数，**含义由 L2 定义**，L1 只比较大小 | 人能站在地毯上，不能站在墙里。L1 不需要知道什么是地毯 |
| h | 连通性 | **L1 提供 `connected(格集合, 起点) → 可达集合`**；`hull_valid` 由 L2 用它拼 | 图连通是通用算法；「船体必须连通」是业务规则 |
| i | 跨层（地面 / 局部网格 / 船内） | **不连通**。`Placement.layer` 不同的格之间没有邻接，过渡由 L2 的「入口」显式建立 | 否则船一靠岸，船内格就和岛上格连成一片 |
| j | 岛屿网格要不要占用表 | **要，但只对当前岛**，且只记「阻挡级」实体 | 村、码头、田块是稀疏的，几百条；玩家不在的岛不需要 |

## 三、设计

### 3.1 三张表，两张是派生的

| | 内容 | 谁是权威 | 进存档 |
|---|---|---|---|
| **静态通行位** | 每格一个 `uint32`：地形决定的可通行方式 | slice（预烘焙） | 否（随 slice 走） |
| **建造通行位** | 墙、门、甲板改动 | `GridBuild` 组件（L2 状态） | 是（在组件里） |
| **占用倒排** | 格 → 实体列表 | `Placement`（L2 状态） | **否**，重建 |

> **只有一份权威状态：实体的 `Placement` 和建造组件。** 其余两张都是它们的函数。
> 这条保证了 `CORE-save` 不必验索引，也保证了不会出现「表和实体对不上」这种最难查的 bug。

### 3.2 接口

```cpp
using Cell   = uint32_t;
using Mask   = uint32_t;          // 通行方式位掩码（口径 c）
using Level  = uint8_t;           // 占用等级（口径 g）

struct Footprint {                // 业务给（口径 f）
    std::vector<std::pair<int16_t,int16_t>> cells;   // 相对偏移
    Level level;
};

enum Conflict : uint32_t {        // L1 只报事实，不做裁决（口径 e）
    None         = 0,
    OutOfBounds  = 1u << 0,
    Impassable   = 1u << 1,
    Occupied     = 1u << 2,
    WrongLayer   = 1u << 3,
};

class Space {
public:
    // 事实查询
    std::span<const EntityId> occupants(Placement) const;
    bool     passable(Placement, Mask mode) const;
    Conflict check(const Footprint&, Placement, Mask mode) const;   // ← 不叫 can_place

    // 连通（口径 h）
    std::vector<Cell> connected(std::span<const Cell> region, Cell from, Mask mode) const;

    // 活动区管理（口径 b）
    void enter(uint16_t island, uint8_t layer);   // 建倒排
    void leave(uint16_t island, uint8_t layer);   // 丢弃
};
```

⚠️ **这里的方法叫 `check` 而不是 `can_place`。** 这个命名是故意的：

> L1 回答的是「**有什么冲突**」，不是「**能不能**」。
> 「能不能」要加上业务规则（靠墙、朝向、许可、花不花得起工料），那是 L2 的 `can_place`。
> 前端查询的是 L2 那个（`PLAN-CORE` C3），L1 这个前端根本看不见。

### 3.3 为什么 `check` 返回位而不是 `bool`

因为 UI 要说人话：「这里过不去」和「这里已经有东西了」是两句不同的提示，
而**那句话必须过棱镜**（禁令）。返回 `bool` 会逼着调用方自己再判一遍原因，
于是判断逻辑就散出去了。

返回位掩码，L2 把位翻译成一个 `reason_key`，棱镜再把 key 渲染成字。
**L1 全程不碰一个字。**

### 3.4 层不连通（口径 i）

`Placement.layer` 把空间切成互不邻接的几片：地面、局部网格、船内。

> 船靠岸时，船内的格**不会**和岛上的格连成一片。
> 过渡是 L2 显式建立的「入口」（舷梯、门），不是几何邻接。

这条不定，会出一个很荒诞的 bug：**船一停靠，村民就能顺着甲板走进你的船舱**。
更糟的是船开走之后他还在。

### 3.5 与引擎的分界（`PLAN-CORE` C1 / C3 的落地）

| | core（本系统 + L2） | 前端（UE） |
|---|---|---|
| 一格能不能进 | **权威** | 查询，不复算 |
| 一样东西能不能摆 | **权威**（L2 的 `can_place`） | 半透明预览、红色高亮 —— 查询结果的可视化 |
| 角色走路时绕开桌腿 | 不管 | 碰撞体与贴地 |
| 室内从门口走到柜台 | 不管 | navmesh |
| 静态通行位怎么来的 | slice 预烘焙 | **不得自己从模型重算** |

⚠️ 最后一行是实践中最容易破的：美术摆了一堵墙，建模里有碰撞体，但没进 slice 的通行位。
**结果是前端走不过去、后端认为能走，NPC 卡在墙里。**
解法：通行位由 slice 烘焙**并且**导出成前端可用的形式，前端的碰撞体**从它生成**，
而不是美术手摆。这条要写进将来的美术管线约定。

## 四、校验

| id | 内容 | 硬 / 软 |
|---|---|---|
| `SPC-derive` | 占用倒排是 `Placement` 的函数：任意时刻重建，与增量维护的表逐字节一致；存档里不含占用表 | 硬 |
| `SPC-sym` | 放置后 `occupants` 含它，移除后不含；`enter` / `leave` 往返后表一致 | 硬 |
| `SPC-mask` | 源码扫描：L1 的空间模块里没有任何具名移动方式、没有具名占用等级 | 硬 |
| `SPC-layer` | 不同 `layer` 的格永不相邻：`connected` 不会跨层返回格 | 硬 |
| `SPC-conn` | `connected` 与朴素洪泛结果集合相同，且返回顺序确定（按 `Cell` 升序） | 硬 |
| `SPC-rot` | 足迹按八向旋转四次回到原位；旋转是纯整数，无浮点 | 硬 |
| `SPC-reason` | `check` 的每一个冲突位都有对应的 L2 `reason_key`，且没有裸字符串（与 `CORE-render` 合并验） | 硬 |

## 五、实施步骤

| 步 | 内容 | 做完能看到什么 |
|---|---|---|
| 1 | `Cell` · `Mask` · 静态通行位从 slice 烘焙并加载 | 终端里问「这格能走吗」有答案；`SPC-mask` 转绿 |
| 2 | 占用倒排 · `enter` / `leave` · `occupants` | `SPC-derive` / `SPC-sym` 转绿 |
| 3 | `Footprint` · 八向旋转 · `check` 与冲突位 | 终端里摆东西、被拒绝并说得出原因；`SPC-rot` / `SPC-reason` 转绿 |

| 5 | 并进 L1 独立测试套件（`CORE-layer` 的正面校验） | 空间系统在一个没有游戏概念的测试里跑通 |

## 六、风险

- **「顺手在 L1 里判一下靠墙」。** 这是本系统最可能被污染的地方，因为业务规则天然想贴着占用表写。
  `SPC-mask` 只扫得到具名常量，扫不到藏在条件里的规则。**`check` 这个命名是第一道防线**——
  一个叫 `check` 的东西返回 `bool` 就很奇怪，返回冲突位就很自然。
- **占用表被改成权威。** 增量维护一张表比每次重建快，诱惑很大；一旦它成了权威，
  就会和 `Placement` 分叉，而且分叉之后**没有任何办法发现**（两边都「看起来对」）。
  `SPC-derive` 每次都重建比对，宁可慢。
- **活动区边界。** 玩家站在岛边看着海对面的岛，那个岛的实体在不在活动区？
  默认不在——但这意味着「远处那艘船在哪」只能靠 `Placement` 全表扫。够用，但别让它悄悄变成
  「把所有岛都 `enter` 一遍」。
- **静态通行位与美术不同步**（§3.5 最后一行）。这是跨工种的坑，代码里挡不住，要写进美术管线约定。
- **足迹旋转的原点。** 1×2 的床绕哪个格转？定错了会在八个朝向里有四个偏一格。
  `SPC-rot` 验的是「转四次回到原位」，**这挡不住系统性偏移**——要额外手验一次。
