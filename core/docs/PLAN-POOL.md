# 数值池与伤害设计稿：一个带上下限的整数，和一次有来源的增减

> 状态：**设计稿，未实施**（2026-09-19）。上游 `PLAN-CORE.md` 第五节底层清单 **#6 数值池**。
> 与 `PLAN-CLOCK` / `PLAN-ENTITY` / `PLAN-SPACE` 同属 **L1 机制层**（分层规则见 `PLAN-CORE` 第四节）。
>
> 写给一段时间没看项目的人：**先读一、二两节就够决定**。
>
> **一句话**：伤害系统的底层不是「战斗」，是**一个有上下限的池子 + 一次带来源的增减**。
> 它不知道什么是刀、什么是风暴、什么是抗性。

---

## 一、要解决什么

首版不做战斗（`docs/09` 把兼并者限定为压力源，不做国战）。
但战斗要素在设计里一直都有：

- `docs/02` §八 **战争形态**
- `docs/02` 稀疏岛链的生计：渔猎 + 中转贸易 + **劫掠**；`docs/11` §八「常年劫掠与贸易并行」
- 九格表第 ⑥ 行 **军事**（`docs/08`）
- `docs/07` §六 雇佣船长「会出问题：风、**劫**、罢工」
- `docs/05` 破城之夜

**所以这个系统迟早要来。它现在就该建，理由不是「快要用了」，而是：**

> 底层由「这是一台什么机器」决定，不由「这台机器现在跑什么内容」决定。
> **如果等战斗来了再设计它，它会在业务压力下诞生，一出生就是脏的**——
> 那时它会长着「伤害类型」「护甲」「暴击」这些业务概念，再也拆不干净。

而且它**现在就有用户**，只是没人管它们叫伤害：

| 用它的地方 | 池 | 增减的来源 |
|---|---|---|
| 船体耐久 | 耐久 | 风暴、撞击、劫掠、维护 |
| 人的伤病 | 健康 | 劳损、疫病、受伤、医治 |
| 作物 | 长势 | 旱、涝、霜、虫、照料 |
| 建筑 | 完好 | 风蚀、失修、修缮 |
| 载重 | 已载 | 装货、卸货 |
| 库存 | 存量 | 收获、消耗、腐坏 |

**六个系统，一套机制。** 这正是原语二（一种存储服务四个系统）的同一种想法。

## 二、需要拍板的口径（有默认值，可直接说「按默认」）

| # | 问题 | 默认 | 说明 |
|---|---|---|---|
| a | 池的表示 | **`{value, min, max}` 全整数** | 确定性纪律第 3 条。浮点只留表现层 |
| b | 负数 | **允许**（`min` 可以是负） | 「欠」也是池。载重不会为负，但账目会 |
| c | **抗性 / 减免谁算** | **L2**。L1 只做 `apply` 与钳制，**不得出现任何公式** | 这是本稿最要紧的一条。L2 算出最终增减再递进来，L1 收到的已经是结果 |
| d | 增减的形状 | **`{pool, delta, source_kind, source_entity, day}`**，`source_kind` 是 `uint32`，L1 不认识 | 与 `EventBus` 的 `kind` 同一套纪律 |
| e | 钳制后的溢出量 | **返回**：挡掉多少、溢出多少 | 业务要用：满仓装不下的货要退回，过量伤害要转成别的效果 |
| f | 变动进不进存档 | **不进**。池的**当前值**进存档；变动走 `EventBus` | 一局几十万次变动。需要历史的池由 L2 自己挂一个 `Journal`（口径 g） |
| g | 需要历史怎么办 | **L2 自己挂 `Journal<自己的条目>`** | 「船是怎么坏的」值得记，「载重变了几次」不值得。由业务决定 |
| h | 阈值触发 | **L1 只报「这次跨过了哪些注册的整数阈值」**，含义归 L2 | 船沉、人死、仓满都是跨阈值。L1 不知道跨过 0 意味着沉船 |
| i | 一个实体几个池 | **`Pools` 组件**：一组具名池，名字是整数 id（`Store<Pools>`） | 一艘船同时有耐久与载重 |
| j | 随机 | **不在本系统**。随机减免由 L2 用 `entity_rng` 算好再 `apply` | `PLAN-CORE` §11.3；L1 的池是纯函数 |
| k | 增减的顺序 | **按调用顺序**，同一帧内不排序、不合并 | 合并会改变跨阈值的时机（先扣到 0 再加，和先加再扣，结果不同） |

## 三、设计

### 3.1 池

```cpp
struct Pool {
    int64_t value;
    int64_t min;      // 允许为负（口径 b）
    int64_t max;      // 上限；无上限用 INT64_MAX
};

struct Pools {                      // 组件，挂在实体上（口径 i）
    std::vector<uint32_t> name;     // 池名（整数 id），升序
    std::vector<Pool>     pool;     // 平行数组
    std::vector<int64_t>  thresh;   // 已注册阈值，按 (name, 值) 升序
};
```

数组保持有序 ⇒ 遍历确定、序列化稳定（与 `PLAN-ENTITY` §3.3 同一条纪律）。

### 3.2 一次增减

```cpp
struct Delta {
    uint32_t pool;            // 池名
    int64_t  amount;          // 已经算完抗性的最终值（口径 c）
    uint32_t source_kind;     // L2 定义，L1 不认识（口径 d）
    EntityId source_entity;
    int32_t  day;
};

struct Applied {
    int64_t before, after;
    int64_t blocked;                    // 被钳制挡掉多少（口径 e）
    int64_t overflow;                   // 溢出多少
    std::vector<int64_t> crossed;       // 这次跨过了哪些阈值（口径 h），升序
};

Applied apply(Pools&, const Delta&);    // 纯函数式：同样的输入永远同样的输出
```

**`apply` 的全部内容**：

```
before = value
after  = clamp(value + amount, min, max)
blocked  = |期望变化| − |实际变化|
overflow = 超出 max（或低于 min）的那部分
crossed  = 注册阈值里落在 (before, after] 或 [after, before) 的那些
value = after
发一个 Event(kind=source_kind, subject=实体, object=source_entity, a=amount, b=after)
```

**没有别的了。** 没有抗性、没有类型、没有暴击、没有免疫、没有「最少扣 1 点」。
那些全是 L2 在算出 `amount` 之前做的事。

> ⚠️ **口径 c 是这份稿子的全部价值所在。**
> 一旦 `apply` 里出现第一个公式——哪怕只是「护甲减伤不低于 10%」——
> 这个系统就从底层掉到业务层了，而且**再也回不去**：
> 下一个需求会往里加第二个公式，半年后它就是一个谁也不敢动的伤害计算器。

### 3.3 为什么要报 `blocked` 和 `overflow`

因为业务几乎总要用：

- 满仓装不下的那部分货**要退回码头**，不能凭空消失
- 过量伤害在有些设计里转成别的效果（船沉、人昏迷）
- 补满之后多出来的照料**不该被静默吞掉**——否则玩家会觉得自己白干了

只返回新值的 `apply` 会逼着调用方自己再算一遍，**于是钳制逻辑就有了两份**。

### 3.4 为什么阈值只报整数

`crossed` 返回的是「跨过了哪些值」，不是「发生了什么」。

> L1 不知道跨过 0 意味着沉船，跨过 `max` 意味着仓满。
> 它只知道有人注册了几个整数，而这次变化越过了其中的哪几个。

L2 拿到 `crossed` 去查自己的表，决定发什么事件、排什么日程。
**这和 `Timeline` 把 `Handle` 原样还回去是同一种做法**（`PLAN-CLOCK` §4.2）。

### 3.5 和其他底层系统的关系

| | 关系 |
|---|---|
| `Store<T>`（#2） | `Pools` 是一个普通组件，用同一套存储 |
| `EventBus`（#4） | 每次 `apply` 发一个事件，`kind` 由 L2 给 |
| `Journal<T>`（#3） | **不自动写**。要历史的池由 L2 自己挂（口径 g）——自动写就是污染 |
| `Timeline`（#1） | 周期性的增减（腐坏、风蚀、长势）由 L2 排期，池自己不带时间 |
| `Rng`（#7） | 池里没有随机。随机在 L2 算 `amount` 时用 |

⚠️ 最后一行值得强调：**池是纯函数。** 同样的 `Pools` 加同样的 `Delta`，
在任何机器、任何编译器上都得到同样的结果——这是它能进 `CORE-replay` 的前提。

## 四、校验

| id | 内容 | 硬 / 软 |
|---|---|---|
| `POOL-clamp` | `apply` 后 `value` 永远在 `[min, max]`；`blocked` / `overflow` 与朴素计算一致 | 硬 |
| `POOL-det` | 同一串 `Delta` 重放两次，每一步的 `Applied` 逐字段相同；跨编译器也相同 | 硬 |
| `POOL-thresh` | `crossed` 与「逐 1 递增地走一遍」得到的跨越集合相同；方向（增 / 减）都验 | 硬 |
| `POOL-order` | 打乱同日 `Delta` 的顺序会改变结果——**这是预期行为**，测试固定顺序并断言不做合并（口径 k） | 硬 |
| `POOL-nopolicy` | **源码扫描**：`src/mech/pool` 下没有任何浮点、没有百分比常量、没有业务词表里的标识符（`armor` / `damage_type` / `crit` / `resist` …） | 硬 |
| `POOL-nostate` | 存档里只有池的当前值与阈值，没有变动历史 | 硬 |

`POOL-nopolicy` 是本稿的主防线，直接对应口径 c。

## 五、实施步骤

| 步 | 内容 | 做完能看到什么 |
|---|---|---|
| 1 | `Pool` · `Pools` 组件 · 序列化 | 终端里给一艘船挂耐久与载重两个池；存档往返 |
| 2 | `apply` · 钳制 · `blocked` / `overflow` | `POOL-clamp` / `POOL-det` 转绿 |
| 3 | 阈值注册与 `crossed` | `POOL-thresh` 转绿；L2 能拿它做「跌破 0 就沉船」 |
| 4 | 发事件接入 `EventBus` | `POOL-nostate` 转绿 |
| 5 | `POOL-nopolicy` 源码扫描进 `zhouzhu_check`；并进 L1 独立测试套件 | 公式从此进不来 |

**第 5 步不要往后挪**（与 `PLAN-CLOCK` 第 5 步同理）：每晚一天，就多一分被塞进公式的机会。

## 六、风险

- **口径 c 会被「就加一个小公式」反复挑战。** 而且每一次听起来都合理：
  「护甲减伤不低于 10%」「最少扣 1 点」「过量伤害减半」。
  **它们全都属于 L2**，理由不是洁癖——是因为这些数字会随平衡调整不停地改，
  而底层的定义是**不会变**。一个会随平衡改的东西放进底层，底层就不是底层了。
- **`Journal` 自动挂。** 「既然每次都发事件，不如顺手记一条」——一记，池就知道了自己该被记录，
  下一步就是知道「哪种变动值得记」，那已经是业务判断了。
- **合并同帧增减。** 看起来是优化，实际会改变跨阈值的时机（口径 k）。
  先扣到 0 再加 5，和先加 5 再扣，`crossed` 完全不同——而「是否跌破 0」往往决定生死。
- **池名用枚举。** 如果 L1 里出现 `enum PoolName { Durability, Health }`，就污染了。
  池名必须是 L2 给的整数。
- **战斗来临时的回归压力。** 真做战斗时，一定会有人想「在池里加个伤害管线更方便」。
  那时本稿要被重读一遍——**`POOL-nopolicy` 就是为那一天准备的。**
