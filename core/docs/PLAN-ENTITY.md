# 实体与存储设计稿：一个永不复用的号码，和二十个按号码排好队的数组

> 状态：**设计稿，未实施**（2026-09-19）。上游 `PLAN-CORE.md` 第五节底层清单 **#2 存储**。
> 这是 core 的第一块地基：账本挂在谁身上、田块属于谁、船上载着谁、物品有没有身份，全从这里长出来。
>
> 写给一段时间没看项目的人：**先读一、二两节就够决定**；第三节是设计，第四节起是验收与实施。
>
> 本稿全部属 **L1 机制层**，分层规则与防污染防线见 `PLAN-CORE.md` 第四节——不得出现任何业务标识符。
> ⚠️ 唯一的例外是 §3.6 的「有没有来历」判据：那是**业务规则**，只是写在这里便于理解；
> 实现时它属 L2（`PLAN-CORE` §6.2）。

## 一、要解决什么

D-H 定了组合式建模：NPC = Placement · Ledger · Predicament · Schedule，村 = Placement · Population · Locale，
以此类推。那是**形状**。真正没有答案的是下面这些，而它们每一条都会在半年后以静默 bug 的形式讨回来：

| 问题 | 不解决会怎样 |
|---|---|
| 实体用什么标识，能不能回收 | id 一旦回收，三年前那条「她替你修过船舵」会指到另一个人身上 |
| 实体怎么销毁 | NPC 死了，账本里提到她的条目还要能渲染；直接删掉就是悬空引用 |
| 组件存在哪，怎么遍历 | 遍历顺序决定确定性（`CORE-replay`）。一个 `unordered_map` 就够毁掉重放 |
| 实体之间怎么互相指 | 关系网的边、田块属于哪个村、船上载着谁、账本挂在谁身上 |
| 「这一格上有什么」怎么答 | 网格建造的 `can_place` 靠它；而它又不能进存档（派生品） |
| 一袋谷和你爹的秤是不是一类东西 | **第三幕头一件事就是那杆秤作废**。没有个体身份，这个情感落点不存在 |

**本稿的目标：把实体、组件、物品、容器这四样定死，定到可以直接写 `struct` 的程度。**

## 二、需要拍板的口径（有默认值，可直接说「按默认」）

| # | 问题 | 默认 | 说明 |
|---|---|---|---|
| a | `EntityId` 分不分类型 | **不分**。单一 `struct EntityId { uint64_t v; }`，强类型只用来挡住「裸整数传错」 | 分类型（NpcId / ShipId …）要模板，D-L 禁 TMP；而且组合式建模里「种类」本来就是「有哪些组件」的结果，钉死在 id 里是自相矛盾 |
| b | id 起点与保留值 | **`0` = 无效（null）**，玩家固定 `1`，其余从 `2` 起单调递增 | `PLAN-CORE` §8.2 的 `observer` 用的就是这个约定 |
| c | 计数器进不进存档 | **进**。它是世界状态的一部分 | 不进存档则读档后新实体的 id 会和重放时不同，`CORE-replay` 立刻挂 |
| d | 实体怎么销毁 | **不真删**。`Identity` 记录永久保留（id / kind / 名字键 / 生灭日期 / `alive`），**组件可以删** | 账本、事件日志、关系网都可能引用它。死了的 NPC 不再需要 `Schedule`，但她的 `Identity` 要活到存档结束 |
| e | 组件存哪 | **每种组件一个按 id 升序的密集数组 + 一张 `vector<int32_t>` 查找表（下标就是 id）** | id 单调不复用 ⇒ id 本身就是密集下标，不需要哈希。见 3.3 |
| f | 组件删除怎么删 | **稳定移除**（保持 id 升序），不用 swap-and-pop | 数组永远有序 ⇒ 遍历顺序天然确定，不必每次排序。规模几千，移动开销无所谓（D-L） |
| g | 实体之间怎么指 | **一律存 `EntityId`**，不存指针、不存下标 | 下标会随数组增删漂移；指针不能序列化 |
| h | 空间查询怎么答 | **首版全表扫**；只有局部网格的 `occupants` 例外，**进入地点时按需建索引，离开时丢弃** | `can_place` 在建造预览里会跟着光标高频调用。**索引是派生品，不进存档**（通则见 3.5） |
| i | 物品：量 vs 个体的判据 | **看有没有来历**。通过账本事件得来的（赠予 / 继承 / 亲手所制 / 定制）是**个体**；买来的、收获的是**量** | 这条判据是主题性的，不是技术性的：有来历的东西才有情感重量 |
| j | 量的单位存什么 | **只存基准单位的整数**，地方单位（斗 / 石）只活在棱镜层 | 「20 斗谷」里的「斗」是地方口径。基准量进存档，facade 收 intent 时就换算掉。**这是中性数据禁令在存储层的落法** |
| k | 个体物品是不是实体 | **是**，有 `EntityId` + `Provenance` 组件 | 它要被账本引用、要能渲染来历、要能传给别人 |
| l | 容器怎么表示 | **`Inventory` 组件**：一组量 + 一组个体 id | 船（载重受限）、主家（无限）、城镇寄存共用同一个组件，差别只在容量上限 |
| m | 组件增删要不要记事件 | **要**，记进事件日志 | 居民迁来 = 多一个组件，那是世界里发生的事，风评与 fold 都可能要它 |
| n | 序列化 key 顺序 | **`nlohmann::json` 默认**（底层有序 `std::map`），不用 `ordered_json` | 有序 map 的 key 顺序由内容决定，与插入顺序无关 ⇒ `CORE-save` 的逐字节一致天然成立 |
| o | 组件类型表在哪 | **代码里的枚举 + 编译期注册**，内容层不得新增组件类型 | 新组件类型意味着新的 fold 与序列化规则，那是代码的事（与 `PLAN-CORE` 口径 r 同理） |

## 三、设计

### 3.1 `EntityId`

```cpp
struct EntityId {
    uint64_t v = 0;                       // 0 = 无效
    constexpr bool valid() const { return v != 0; }
    friend constexpr bool operator<=>(EntityId, EntityId) = default;
};

inline constexpr EntityId NONE   { 0 };
inline constexpr EntityId PLAYER { 1 };
```

**永不复用。** 计数器是 `uint64_t`，从 2 起单调递增，进存档（口径 c）。

一局游戏能创建多少实体？几百个 NPC + 几千个村 / 田块 / 船 + 个体物品。
**量（可堆叠的谷、盐、木料）不是实体**，所以最大的那一类根本不占号。估计上限在万级。
`uint64_t` 是为了不用想这件事，不是因为真会用到。

### 3.2 `Identity`：永久记录

每个实体一条，**永不删除**（口径 d）：

```cpp
struct Identity {
    EntityId id;
    uint16_t kind;        // npc / village / ship / field / item / place …（调试与序列化可读性）
    uint32_t name_key;    // 指向内容表的名字键。⚠️ 不是字符串（中性数据禁令）
    int32_t  born_day;    // 世界钟日序；-1 = 开局既有
    int32_t  died_day;    // -1 = 还活着
    bool     alive;
};
```

`kind` 只用于调试、序列化可读性和粗筛，**不得用它做规则判断**——
「这是不是一艘船」的正确问法是「它有没有 `Cargo` 组件」（口径 a）。

⚠️ `name_key` 是键不是字符串。「铁匠」这个称呼在不同地方、不同熟悉程度下说法不同，
那是棱镜的事（`PLAN-CORE` C7）。

### 3.3 组件存储：id 就是下标

因为 id 单调递增且永不复用，**id 本身就是一个密集下标**。于是不需要任何哈希：

```cpp
template <class T>
struct Store {
    std::vector<T>        data;    // 按 owner 的 id 升序，永远有序
    std::vector<EntityId> owner;   // 与 data 平行
    std::vector<int32_t>  index;   // 下标 = id.v；值 = data 里的位置，-1 = 没有这个组件
};
```

- **查**：`index[id.v]`，O(1)，无哈希。
- **遍历**：直接扫 `data`，顺序就是 id 升序 —— **确定性由构造保证，不需要排序，也不会出现 `unordered_map` 那条坑**（确定性纪律第 1 条）。
- **加**：插到有序位置（`std::lower_bound` + `insert`），修正后面的 `index`。
- **删**：稳定移除（口径 f），同样修正 `index`。

代价：插删是 O(n) 的移动。n 是**这种组件**的实例数——几百到几千，一次移动几微秒。
D-L 说得很清楚：省下的复杂度换成「状态是平的、存档是直的、重放是准的」。

内存：`index` 每种组件 4 字节 × 实体总数。二十种组件 × 一万实体 = 800 KB。不用想。

> ⚠️ **不要为了省那点移动改成 swap-and-pop。** 那会让 `data` 失去有序性，
> 遍历顺序变成「历史操作序列的函数」——它仍然是确定的，但从此**没有任何人能靠读代码判断顺序**，
> 而 `CORE-replay` 挂掉时你要靠读代码定位。

### 3.4 实体之间怎么指

一律 `EntityId`（口径 g）。因为记录永不删除，**任何 id 都一定解析得到一条 `Identity`**，
可能是 `alive = false` 的——没有悬空引用这回事。

| 引用 | 存在哪 |
|---|---|
| 账本挂在谁身上 | `Ledger` 组件的 owner |
| 账本条目指向谁 | `Entry.other` |
| 田块属于哪个村 | `Field.village` |
| 船上载着谁 | `Cargo.passengers: vector<EntityId>` |
| 个体物品在谁手里 | `Inventory.items` 反向；正向由 `Placement.layer = 容器内` 表达 |
| 关系网的边 | **单独一张有序表**，不是组件，见下 |

**关系网的边**（`06` §五：亲属 / 师徒 / 旧怨 / 生意伙伴）是实体之间的东西，挂在任一端都不对称。
做成一张按 `(a, b)` 排序的表，`a < b` 归一化，查询时二分：

```cpp
struct Bond { EntityId a, b; uint16_t kind; int8_t strength; };
std::vector<Bond> bonds;   // 按 (a, b, kind) 升序
```

### 3.5 空间查询与索引

**通则：任何索引都是派生品，不进存档，加载后重建。** 否则 `CORE-save` 要连索引一起验，
而索引的构造顺序一变，逐字节一致就挂了——**为一个纯粹的加速结构付这个代价不值**。

| 查询 | 首版做法 |
|---|---|
| 「这个岛上有哪些实体」 | 全表扫 `Placement` 的 `data`（几百到几千条），过滤 `island` |
| 「这一格上有什么」（岛屿网格） | 同上 |
| **`occupants(局部网格格)`** | **按需索引**：进入某个地点（主家 / 前哨 / 船内）时建一张 `cell → vector<EntityId>`，离开时丢弃。**详见 `PLAN-SPACE.md`**——占用与通行已提成独立的底层系统（#5），本稿只负责它的倒排来源 |

只有最后一条给了索引，因为建造预览会跟着光标走，一帧一次 `can_place`。
局部网格的地点**数量是个位数**（`PLAN-CORE` 第九节），一张表几百个格，建一次是微秒级。

### 3.6 物品：量与个体

这是本稿唯一一个**由主题而非技术决定**的设计。

```cpp
// 量：不是实体，是容器里的一行
struct Stack {
    uint32_t kind;    // 指向内容表的物品种类
    int64_t  amount;  // ⚠️ 基准单位的整数（口径 j）。斗 / 石是棱镜的事
};

// 个体：是实体，多一个 Provenance 组件
struct Provenance {
    uint32_t kind;       // 同样指向物品种类——爹的秤首先是一杆秤
    EntityId from;       // 谁给的 / 谁做的；NONE = 自然得来
    int32_t  day;        // 哪一天
    uint64_t entry;      // 账本条目 id；0 = 没有对应条目
    uint32_t note_key;   // 一句话的来历，内容表的键，不是字符串
};
```

**判据（口径 i）：有没有来历。**

| 东西 | 哪种 | 为什么 |
|---|---|---|
| 二十斗谷 | 量 | 买来的，可替代 |
| 一船木料 | 量 | 同上 |
| 你爹留下的那杆秤 | **个体** | 继承，有来历。**第三幕头一件事就是它作废** |
| 铁匠替你打的船舵 | **个体** | 账本上有那一笔（`06` §一），`entry` 指过去 |
| 从北边带回的她父亲的遗物 | **个体** | 同上，而且这是恩情条目的实物 |
| 城里买的同款秤 | 量 | 没有来历——**这正是第三幕的刀口**：官秤重校之后，你可以去换一杆一模一样的新秤，但那不是那杆秤 |

个体照样有 `kind`，所以「当秤用」和「当谷卖」都走同一套规则，
**个体身份不改变它的功能，只改变它的意义**。这正是主题要的。

### 3.7 容器

```cpp
struct Inventory {
    std::vector<Stack>    stacks;    // 按 kind 升序
    std::vector<EntityId> items;     // 个体，按 id 升序
    int64_t capacity;                // 基准单位的载重上限；-1 = 无限
};
```

`07` §二 的三层空间共用这一个组件，差别只在 `capacity`：
空艇有限（**破城之夜最要命的那个数字**）、主家 `-1`、城镇寄存另算。

两个 `vector` 都保持有序 ⇒ 遍历确定、序列化稳定（口径 n 之外的第二重保险）。

### 3.8 组件清单（草案）

每个组件的内部设计归它自己的系统设计稿，本稿只登记**有哪些、挂在谁身上**：

| 组件 | 挂在 | 内容 | 归哪份稿子 |
|---|---|---|---|
| `Identity` | **一切实体** | 见 3.2 | 本稿 |
| `Placement` | 一切有位置的 | `PLAN-CORE` 第九节 | 本稿 / PLAN-CORE |
| `Inventory` | 玩家 · 船 · 主家 · 铺子 | 见 3.7 | 本稿 |
| `Provenance` | 个体物品 | 见 3.6 | 本稿 |
| `Ledger` | 玩家 · 深度 NPC | 账本条目数组 | 另立（账本稿） |
| `Predicament` | 深度 NPC | 处境与时间线 | 另立 |
| `Schedule` | NPC | **日程定义的引用，不是状态**（`PLAN-CORE` 口径 j：日程是纯函数） | 另立 |
| `Knowledge` | 玩家 | `06` §三 的知识条目 | 另立（棱镜稿） |
| `Population` | 村 | 户数、人口 | 另立 |
| `Locale` | 村 · 地点 | 它在文化场里的位置（供棱镜取值） | 另立（棱镜稿） |
| `Field` | 田块 | 归属村、作物、阶段 | 另立（农事稿） |
| `Cargo` | 船 | 载重、舱位、乘客 | 另立（航行稿） |
| `GridBuild` | 船 · 主家 | 局部网格的格局 | 另立（建造稿） |

⚠️ **`Schedule` 存的是定义不是状态**，这是 `PLAN-CORE` 口径 j 的直接后果。
如果哪天有人往里加了「她现在走到哪了」，`CORE-time` 会红。

### 3.9 序列化

每个组件 `NLOHMANN_DEFINE_TYPE_INTRUSIVE`，存档里是：

```
{ "counter": 4413,
  "identity":  [ … ],          // 按 id 升序
  "placement": { "owner": [...], "data": [...] },
  "inventory": { "owner": [...], "data": [...] },
  … }
```

**索引一律不存**（3.5 通则），加载后从 `owner` 重建。
所有数组已按 id 升序 ⇒ 逐字节一致天然成立（口径 n）。

存档版本号在最外层；加字段时版本号 +1，round-trip 测试兜底（没有反射，漏字段是静默的）。

## 四、校验（`CORE-*` 追加）

| id | 内容 | 硬 / 软 |
|---|---|---|
| `ENT-id` | 一局中任何 id 不被复用；销毁后 `Identity` 仍可解析；重放两次 id 分配完全相同 | 硬 |
| `ENT-order` | 每个 `Store` 的 `data` / `owner` 始终按 id 升序；`bonds` 按 `(a,b,kind)` 升序 | 硬 |
| `ENT-index` | `index[id] == data` 中的真实位置；存档里不含任何索引；加载后重建的索引与保存前逐字节一致 | 硬 |
| `ENT-ref` | 任何被引用的 `EntityId` 都解析得到 `Identity`（可以是 `alive=false`），无悬空 | 硬 |
| `ENT-unit` | 存档里没有任何地方单位；所有量是基准单位的整数 | 硬 |
| `ENT-prov` | 每个个体物品都有 `Provenance`；`entry` 非 0 时该账本条目存在 | 硬 |
| `ENT-nohash` | 源码扫描：`src/` 与 `facade/` 里不出现 `unordered_map` / `unordered_set` | 硬 |

`ENT-nohash` 是 `PLAN-CORE` 风险节提的那条「grep 级别的源码扫描」——
别等 `CORE-replay` 在跨编译器时才炸。

## 六、风险

- **有人改成 swap-and-pop。** 性能直觉会反复诱惑。`ENT-order` 挡着，但要在注释里写明原因（3.3 的引文）。
- **有人把 `kind` 当规则用。** 「if kind == ship」比「if has<Cargo>」顺手。
  这会让组合式建模退化成继承，**而 D-H 的全部价值就在于不是继承**。
  暂时没有自动校验能挡，只能靠代码评审——或者干脆不把 `kind` 暴露给规则层。
- **地方单位漏进存档。** `ENT-unit` 只能扫得到明显的（字段名带 dou / shi）。
  真正的风险是有人存了一个「已经换算过的显示值」——那是中性数据禁令的正面违反，
  但存储层看不出来。**facade 收 intent 时就换算掉**是唯一可靠的防线（口径 j）。
- **个体物品爆炸。** 判据 i 是「有没有来历」，而账本事件会持续产生来历。
  一局下来个体物品可能上千——不影响性能，但**影响 UI**：仓库里一堆长得一样却不可堆叠的东西。
  需要 UI 侧的分组显示，而分组的依据只能是 `kind` + 棱镜渲染后的描述，不能是合并存储。
- **`Identity` 永不删除 = 存档单调增长。** 与账本条目增长（`09` 风险 1）是同一类问题。
  账本有压缩策略，`Identity` 没有——一局下来几万条 `Identity` 是几 MB，可以接受，
  但**如果哪天开始给每根木料发 id，这条就崩了**。判据 i 同时也是这个的闸门。
