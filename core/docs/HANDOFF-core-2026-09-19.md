## 二、核心判断（整个讨论的地基）

`docs/09` 与 `docs/10` 各自列的「关键技术点」——存档体积、对白引用账本、时间线调度、文化表合并、第三幕世界改写——**是同一件事的五个面**：

> 一条时间轴上不断追加的条目，加上一层把中性数据渲染成「某人在某时某地的理解」的表示层。

由此推出四个原语 + 一条禁令：

1. **世界钟**——全局唯一时钟（336 日 = 4 季 × 3 月 × 28 日，复用生成器历法）。作物、账本腐坏、处境时间线、风评传播、改制事件全是订阅者。玩家不在场时照推。
2. **只追加事件日志 + fold 出派生状态**——账本、处境、风评、改制共用一种存储：带日期的条目数组。当前关系/态度/风评是数组的 fold，不落盘。一个存储机制服务四个系统，压缩策略只写一次。
3. **棱镜渲染器**——量、日期、文字、物名在数据里中性（`{谷, 34, 本位斗}`、`{第2年, 第197日}`），显示时过 `render(值, 观察者, 地点, 时间)`，输出 `{text, raw, unit, gloss}`。
4. **文化场查询**——`trait(特征, 地点) → 强度`，从连续场取值，不查地区表。生成器 `culture.py` / `probe trait` 已有实现，导出即可。

> **禁令：任何地方都不许把量、日期、地名、物名以成品字符串存下来或写进 UI。**
>
> 理由：第三幕的官秤重校 / 文字统一 / 历法统一，在代码里就是换一张 locale 表。第一天做对 = 三行配置；有一处 UI 写了字面量 = 第三幕要重写全部界面，而那恰恰是整个项目要验证的东西（`docs/09` 的验证目标）。`docs/06` 写的「主题的载体是 UI 的简化」，落到代码上就是这一条。

## 三、已拍板的决策（连理由）

### D-A 前后端分离，core 零引擎依赖

**用户的理由**（原话）：「我觉得 godot 会限制前端渲染的能力（以至于我想换别的前端，比如 ue），而且也会限制我后端的自由度，导致我的代码高度依赖 godot」。

**推论**：进程边界一划，**后端语言也变成可替换的**——不必现在为「将来可能要换」而过度设计。

**关键细化**：分离靠 **facade 的窄口**（编译期纪律）保证，**不靠进程边界**。

```
zhouzhu_core   纯逻辑静态库。不 include 任何引擎、任何 IO、任何前端概念
      ↓
   facade      窄口：intent / query / patch 三个词汇，只收发 POD + 字符串
      ↓
 ┌────┴────┬──────────┬───────────┐
终端客户端   stdio 服务   GDExtension   UE plugin
(直接链)   (给工具用)   (进程内)     (进程内)
```

> ⚠️ **这里有一处对早前说法的修正**：讨论前期（当时还假设后端用 Python）我说过「先定 JSON over stdio」。改用 C++ 后这个顺序**反了**——facade 先定，传输是第二层包装。进程边界只是纪律的一种强制执行手段，需要时随时加（调试、崩溃隔离、做编辑器），不需要时省掉序列化。

### D-B 后端是权威，前端是哑终端

- 后端持全部状态与时钟；前端只持表现状态（镜头、动画进度）。
- **时钟归后端**。前端发 `set_speed` / `advance`，自己不跑表，否则两边必漂。
- **棱镜渲染在后端**（最要紧）。前端可以只用返回的 `text`，但没有办法绕过棱镜。换引擎时第三幕机制一行不用重写。
- **intent 是语义级的**：「装 20 斗谷上船」「对铁匠说这句」「起航去 1592」，不是坐标和按键。
- **逐帧的东西不过边界**：走路、镜头、粒子全留前端。这条不早定，协议会被拖成帧同步。

### D-C core 用 C++（C++20）

**用户指定**。讨论中确认这个选择**比原先建议的 Python 更贴合用户的目标**，不只是口味：UE 原生吃 C++，Godot 通过 GDExtension 也吃 C++，两边都能进程内加载同一个 core，不付 IPC 税；发行是一个 dll/lib，不用打包解释器。

**依赖清单只两行**：`nlohmann/json`（单头）+ `doctest`（单头、编译快）。沿用 generator「不引入 scipy/networkx/pandas」的纪律——**加新依赖要有理由**。

构建：CMake + MSVC 先跑 Windows，但从第一天保持 clang 能编（纯标准 C++，不用 MSVC 扩展）。

### D-D 确定性三纪律（C++ 下必须主动守）

存档做成「种子 + intent 流 + 重放」，确定性是硬要求。C++ 里这三个坑**静默**，埋进去半年后才炸：

1. **不许遍历 `std::unordered_map` / `unordered_set`**——顺序是实现定义的，换编译器版本就变，不报错，只让重放悄悄分叉。用有序容器、排序后遍历、或自写稳定哈希表。**这是最可能出事的一条。**
2. **不许用 `<random>` 的分布**——`std::uniform_int_distribution`、`shuffle` 跨标准库实现结果不同（MSVC vs libstdc++）。自带 PCG 或 xoshiro，分布自己写几行。沿用 generator 的 `entity_rng(seed, stream, key)` 习惯。
3. **一切进存档的量用整数或定点**——载重、日期、户数、账本权重本来就该是整数；浮点只留表现层。

### D-E 3D，前端 UE

**用户判断**。讨论中确认成本结构已经变了：`docs/10` 当年选 2D 的核心论据是「3D 一个岛几天，2D 一个岛几小时」，那是**假设岛要手工做**。现在生成器给出 8000 个岛群的高程、地表、坡度、河湖、可耕地栅格与聚落点位，**3D 地形几乎免费**（heightmap → mesh，landcover → 散布，settlements.json → 摆房子），比手画 2D tile 还便宜。

⚠️ **代价换了位置，没有消失**：地形免费了，**角色建模、骨骼、动画、室内、可交互道具**在 3D 里是 2D 的几倍——而这个游戏的重量偏偏全在人身上。常规解法是风格化（低面数、少量骨骼、不追面部表情、镜头不怼脸）。**这条要早定，它决定所有资产。**（见「未决问题」）

### D-F 位置用整数 `Placement`，不用浮点 transform

```cpp
struct Placement {
    uint16_t island;   // 岛号（或 船 / 地点 的特殊值）
    uint32_t cell;     // 格索引：100 m 岛屿网格，或 1 m 局部网格
    int16_t  ox, oy;   // 格内偏移，定点 1/256 格
    uint8_t  facing;   // 0–7，八向
    uint8_t  layer;    // 地面 / 局部网格 / 船内
};
```

12 字节，全整数，重放精确。前端转 FTransform 是一行：
`FTransform(FRotator(0, P.facing * 45.f, 0), CellToWorld(P) + Offset(P))`。

更一般的位置类型是标签联合：`AtPlace(place_id)` | `OnGrid(island, cell)` | `Aboard(ship, local_cell)` | `EnRoute(route, 已走天数)`。

**离散八向是更优解，不是妥协**：`docs/07` 要的是网格建造——不会想把一张床摆成 37.4°。缩放后端根本不需要（那是美术的事）。

**两级尺度**：

| | 分辨率 | 谁管 | 进存档 |
|---|---|---|---|
| 岛屿网格 | 100 m，来自 generator | 后端权威 | 是 |
| 地点局部网格 | 0.5–1 m，只在主家 / 前哨 / 船内 | 后端权威 | 是 |
| 连续坐标 | 浮点 | 前端 | **否** |

局部细网格是必须的，因为 `docs/07` 的空艇网格建造与主家装修活在这一层（船本身就是一块会移动的局部网格）。只有玩家真正会建造和耕作的那几个地点需要，数量是个位数。角色精确站位存「格 + 格内定点偏移」，重新加载站回格子中心即可。

### D-G 硬线：后端不许有「速度」和「碰撞」

只有「在哪个格」和「什么时候到哪个格」。NPC 日程是「辰时在铺子，午时在码头」，**中间那段路由前端补间**，后端不跑他的脚步。

后端也**不做寻路**——只有一张预计算好的地点间成本图（生成器连顺逆风的航线成本都算好了）。

理由：一旦后端开始算速度和碰撞，它会慢慢长成一个又慢又不准的物理引擎，而且重放立刻失效。

### D-H 组合式实体模型：抄形，不抄 UE 的类型

用户原话：「我没说要用 UObject，而是抄一个差不多就行」。**这条已对齐**。

**采纳**——组合式建模：

| 实体 | 组件 |
|---|---|
| NPC | Placement · Ledger · Predicament · Schedule |
| 村 | Placement · Population · Locale |
| 船 | Placement · Cargo · GridBuild |
| 田块 | Placement · Field |
| 玩家 | Placement · Ledger · Cargo · Knowledge |

存储不必花哨：每种组件一个 `vector` + 一个稀疏索引数组，遍历顺序就是数组顺序，天然确定（与 D-D 第 1 条一致）。

> ⚠️ **一处对早前说法的修正**：讨论前期我说过「不要上 ECS」——那指的是**性能型 ECS**（archetype 存储、cache 对齐），这个项目用不上。**组合式建模是另一回事，已采纳。**

前端照常：一个后端实体 → 一个 `AActor`，后端组件 → 对应的 `UActorComponent`，中间一层薄映射（几百行，机械的）。**同一个模型，两套类型，一层转换**；换引擎时换那一层，core 一行不动。

### D-I 存档 = 种子 + intent 流 + 周期快照

后端确定性 → 重放即得状态。白拿三样：bug 可精确复现、回归测试就是重放一段存档、CORE-time 可自动验证。快照只是加载加速，不是真相。

### D-J 内容外置，内容侧逻辑用 JSON 谓词树

`docs/10` 的「数据驱动是硬要求」在 C++ 下从「最好这样」升级成「不这样就做不下去」。

- **数值与表**（文化主表、偏移量、微差、九格表、NPC、物产）：全外置 JSON，运行时热重载。
- **内容侧逻辑**（事件触发条件、对白分支、处境时间线判据）：倾向 **JSON 谓词树**（约两三百行），而非嵌 Lua。谓词树能在加载时静态校验「这条微差引用的标签存在吗」，是 generator `check` 纪律的延续。**（未最终拍板，见未决问题）**

### D-K CORE-* 校验（沿用 generator 的 check 纪律）

| id | 内容 |
|---|---|
| CORE-time | 离场推进 30 天 == 在场逐日推进 30 天，派生状态逐字节相同 |
| CORE-fold | 账本压缩前后，所有派生量（态度、欠与被欠、风评标签）不变 |
| CORE-render | 静态断言：没有裸字面量的量 / 日期 / 物名进入 UI 层 |
| CORE-locale | 切 locale 后既有契约、物品、节日日期全部重渲染，不留旧值 |
| CORE-save | 存档往返 save→load→save 逐字节一致 |

CORE-fold 不是形式主义：账本要压缩、条目要腐坏，若压缩改变 fold 结果，存档久了 NPC 会无缘无故性情突变——这种 bug 半年后才暴露。

### D-L 不为性能做任何设计

状态规模：几百个 NPC、几千条账本条目、两个邦。`std::vector<T>` + 整数 id 够到天荒地老。**不上 ECS，不做对象池，不用模板元编程。** 省下的复杂度换成「状态是平的、存档是直的、重放是准的」。

## 四、被否决的方案（连否决理由）

| 方案 | 谁否的 | 理由 |
|---|---|---|
| Godot 4 + GDScript 起步（`docs/10` 原选型） | 用户 | 限制前端渲染能力；且会让后端代码高度依赖 Godot |
| Python 写后端（我最初的建议） | 用户 | 要用 C++。事后确认 C++ 对「引擎可换」的目标确实更对 |
| 2D 俯视（`docs/10` 原结论） | 用户 | 改做 3D；且生成器已让 3D 地形近乎免费 |
| `UObject` / `AActor` / `UActorComponent` 进 core | 我提出，用户接受 | 依赖 UHT 代码生成与 UE 的 GC，**在 UE 之外编译不了**。后果具体：`zhouzhu_check` 与单测要拉整个 UE 才能跑（CI 从几秒变几十分钟）、终端客户端没了、改一行规则要走 UBT。而且「不想依赖 Godot」换成「依赖 UE」是同一种病换名字 |
| `FVector` / `FTransform` 进权威状态 | 我提出，用户接受 | 浮点（UE5 LWC 下是 double）进存档等于交出重放的精度保证；且会把后端往速度/碰撞方向拖。离散八向对网格建造反而更对 |
| 性能型 ECS（archetype / cache 对齐） | 我提出 | 规模太小，纯属自找复杂度。**注意：组合式建模已采纳，两者不是一回事** |
| 一开始上 gRPC / protobuf | 我提出 | schema 还在大改。JSON over stdio 够用（单人游戏每次几 KB），嫌慢再换 MessagePack |
| 嵌 Lua 做内容侧逻辑 | 倾向不做 | 多一个依赖、确定性要额外守、错误在运行时才炸。**未最终拍板** |
| `docs/09` 开发顺序第一步「纸面原型（不写代码）」 | 我建议改 | 改为**可跑的文本原型**（终端、2 邦、5 NPC、5 条微差、三幕压成 40 分钟）。要验证的两件事——破城时会不会犹豫、三件改制后有没有失落——是文本与时间的函数，不是像素的函数；成本是做场景的 1/20，而写出的数据结构就是最终的数据结构。**用户未回应，仍属未决** |

### 关于「C++ 没有反射」

用户专门问过这是不是我的顾虑。**答案是不是。** 记录在此以免重复讨论：

- 我真正担心的**只有一条**：改内容要重编译。**已被 D-J 的内容外置解决**，解决之后不再是问题。
- D-D 的三条不是「C++ 缺功能」，是「C++ 不替你挡」——Python 的 `set` 遍历顺序同样不保证，只是在 generator 里已经形成习惯了。
- 反射在这个项目里的三处用途，基本不疼：

| 用途 | 没反射会怎样 | 做法 |
|---|---|---|
| 存档序列化 | 加字段要改两处，漏了静默丢字段 | `NLOHMANN_DEFINE_TYPE_INTRUSIVE` + round-trip 测试兜底 + 存档版本号 |
| 调试面板 / 状态查看器 | 要给每类型手写 dump | **不用写**——状态本来就过 JSON，面板直接吃序列化结果。序列化就是穷人的反射 |
| 谓词树引用字段 | 要手写「字段名 → 取值函数」注册表 | 几十行显式注册表；让拼错字段名变成**加载时报错**，缺点转优点 |

C++26 静态反射（P2996）已进标准但编译器支持还早，别指望。真烦了再考虑 `boost::pfr`（状态本来就该是聚合体），但那是「疼了再说」。

## 五、未决问题（需要用户拍板）

按影响面排序：

1. **美术风格化的程度** —— 决定所有资产。3D 的成本全在角色与建筑上，这条不定，后面每个资产决策都悬空。
2. **地点局部网格取 0.5 m 还是 1 m** —— 直接决定数据模型。**我倾向 1 m**：主家院子几十米见方就是几千格，船体网格本来也是米级（一格放一个箱子/一张床正合适），0.5 m 让建造操作琐碎且格数翻四倍。除非想要更精细的室内摆设。
3. **内容侧逻辑：JSON 谓词树 vs 嵌 Lua** —— 倾向谓词树（理由见 D-J 与否决表）。
4. **`docs/09` 第一步是否从「纸面原型」改成「可跑的文本原型」** —— 我建议改，用户未回应。
5. **存档序列化格式** —— 建议 JSON 起步（可读、可 diff、bug 可贴出来），留版本号，要小再换二进制。快照间隔也未定。
6. **slice 包具体包含什么** —— 从 seed42 挑**两个真实节点**导出：地形与聚落、逐日天气、人口与政治、两地间航线成本与顺逆风差、两份九格表（要填）。⚠️ **generator 是 Python，别让 C++ 读 npz**——Python 侧导出 JSON + 裸二进制栅格（带小 header），C++ 几十行读完。
7. **首版那两个邦选哪两个节点** —— 这让 `docs/DECISIONS.md` 的 Q14（整个文明圈的地区划分）从大工程缩成「填两张表 + 定 5 条微差」，Q15 同理。

**已实质解决但没明说的一个**：UE 是终点还是可换前端？用户选了「抄形不抄类型」，等于选了**可换前端**。按此推进。
