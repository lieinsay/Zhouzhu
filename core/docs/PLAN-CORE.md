## 一、要解决什么

生成器做完了世界：八千个岛群的地形、气候、逐日天气、聚落、人口、诸邦、文化场。
**但那是一张死的世界。** 没有时间在走，没有人记得你做过什么，没有一样东西会因为你不在而改变。

游戏本体要的是另一件事：**让这张世界活着推进，并且让同一件事在不同的人眼里读出不同的意思。**

`docs/09` 与 `docs/10` 原版各自列过「关键技术点」——账本存档体积、对白引用条目、时间线调度、
文化表合并、第三幕世界改写。**这五件事是同一件事的五个面**：

> 一条时间轴上不断追加的条目，加上一层把中性数据渲染成「某人在某时某地的理解」的表示层。

底层要交付的就是这个，外加一条**画清楚的引擎分界线**——哪些东西换引擎时一行不用动，
哪些东西本来就该交给引擎，以及两边都要有的那几样怎么防止分叉。

## 二、已拍板的决定（2026-09-18，`docs/DECISIONS.md` D73–D76）

| # | 决定 | 含义 |
|---|---|---|
| 1 | **前后端分离，`zhouzhu_core` 零引擎依赖** | 纯逻辑静态库，不 include 任何引擎、任何 IO、任何前端概念 |
| 2 | **分离靠 facade 窄口，不靠进程边界** | 三个词汇 intent / query / patch，只收发 POD + 字符串。**facade 先定，传输是第二层包装**；进程边界需要时再加 |
| 3 | **C++20，依赖只两行** | `nlohmann/json`（单头）+ `doctest`（单头）。UE 与 Godot 都能进程内加载同一个 core，不付 IPC 税 |
| 4 | **后端是权威，前端是哑终端** | 时钟归后端；**棱镜渲染在后端，前端没有办法绕过**；intent 是语义级的；逐帧的东西不过边界 |
| 5 | **后端不许有速度和碰撞，不做寻路** | 只有「在哪个格」和「什么时候到哪个格」。一旦算速度和碰撞，它会长成一个又慢又不准的物理引擎，且重放立刻失效 |
| 6 | **权威状态全整数**，`Placement` 12 字节 | 浮点只留表现层。离散八向对网格建造反而更对 |
| 7 | **存档 = 种子 + intent 流 + 周期快照** | 重放即得状态。快照只是加载加速，不是真相 |
| 8 | **确定性三纪律** | 不遍历 `unordered_map`；不用 `<random>` 的分布；进存档的量全整数或定点 |
| 9 | **组合式实体模型，抄形不抄 `UObject`** | 每种组件一个 `vector` + 稀疏索引。**不上性能型 ECS**（两者不是一回事） |
| 10 | **中性数据禁令** | 量 / 日期 / 地名 / 物名不许以成品字符串存下来或写进 UI |
| 11 | **内容外置，运行时热重载** | 在 C++ 下这从「最好这样」升级成生存条件 |
| 12 | **不为性能做任何设计** | 几百 NPC、几千条账本条目。`std::vector<T>` + 整数 id 够到天荒地老 |

**第四节是已否决的，别再提议**（见 `docs/DECISIONS.md` 作废清单）：Godot + GDScript 起步、2D、
Python 后端、`UObject` / `FVector` 进 core、性能型 ECS、一开始上 gRPC。

## 五、引擎分界线：哪些系统不依赖引擎，哪些依赖

> **这一节是本稿的重点。** 「core 零引擎依赖」是对 core 说的，不是对整个游戏说的。
> 依赖引擎不是坏事，**不写明才是**：不写明会出两种病——规则悄悄漏到前端（换引擎时才发现），
> 或者为了「纯净」把该用引擎的东西硬塞进 core（于是 core 里长出半个物理引擎，正是第二节第 5 条要防的）。

### 5.1 两条判据

> **判据一：它的输出会不会进存档、会不会改变别人的状态、会不会影响重放。**
> 会 → core。不会 → 前端。
>
> **判据二：两边都需要时，core 是权威，前端只查询、不复算。**

### 5.2 A 类 —— core 独占，零引擎依赖

世界钟与调度 · 账本与 fold · 处境时间线 · 文化场与棱镜 · 知识与把握度 · 行为标签与风评 ·
格占用与可放置 · 航线成本与天数 · 载重与库存 · 田块状态 · 事件日志与 intent 流 · 存档格式。

### 5.3 B 类 —— 前端独占，随便依赖引擎

骨骼动画 · 粒子与天气特效 · 镜头 · 音频 · 贴图与 LOD · 角色走路的补间 ·
岛上与室内的 navmesh 寻路 · UI 排版与字体 · 输入设备 · 光照与后处理。

**判据**：把它整个删掉，世界的真相不变，存档不变，重放不变。

### 5.4 C 类 —— 分裂区：两边都要有一份

**漂移只可能从这里发生，所以每条都要写明「前端拿什么、怎么拿、不准做什么」。**

| # | 能力 | core 那半（权威） | 引擎那半 | 前端不准做 | 不写明会怎样 |
|---|---|---|---|---|---|
| C1 | **阻挡 / 通行** | 离散格通行性：崖缘 / 水面 / 漫滩 / 被占用 → 不可进入。进存档，决定 NPC 能不能走到码头 | 角色碰撞体、贴地、绕开桌腿、楼梯 | **不准自己判定一格能不能进** | 碰撞体是美术手摆的 → 玩家卡在 core 认为能走的格里，或走到 core 认为不可达的地方 |
| C2 | **寻路** | 地点之间的成本图（generator 已算好，含顺逆风）：「从 A 到 B 要 9 天」 | 岛上 / 室内走到铺子门口的 navmesh | **不准把 navmesh 的结果回灌成航程** | 不写明「这是两级」，就会有人想在 core 里做 A\* |
| C3 | **网格建造合法性** | `can_place(实体, Placement) → bool` 是权威 | 半透明预览、红色高亮 | **不准为了做预览自己算一遍**，只能 query | 两份规则，迟早分叉；玩家摆得出后端不认的布局，存档一读回来东西全没了 |
| C4 | **NPC 位置** | 「辰时在铺子，午时在码头」，应是纯函数 `f(NPC, 时刻)` | 中间那段路的补间 | **补间途中不准触发任何东西** | 补间「路过」某处若触发了什么，重放立刻失效 |
| C5 | **存档 IO** | 产出字节流，定格式与版本号；**core 不含任何 IO** | 宿主负责落盘、云存档、错误处理 | — | core 里混进文件 API，终端客户端和 CI 就不干净了 |
| C6 | **输入 → intent** | 只收语义 intent | 键鼠 / 手柄 / UI 翻译成语义 | **不准把坐标和按键塞进 intent** | 协议被拖成帧同步（第二节第 4 条已警告） |
| C7 | **文本** | 值 → 字符串（棱镜：单位换算、日期、物名、把握度措辞） | 字符串 → 像素（字体、换行、富文本） | **不准做数字格式化、不准拼接量词** | 绕过棱镜 → 第三幕改不动它 → 整个项目要验证的东西没了 |
| C8 | **时间的显示** | 权威时刻与日期，`advance` / `set_speed` 由前端发起但由 core 执行 | 时钟动画、昼夜光照插值 | **不准自己跑表** | 两边必漂（第二节第 4 条） |

### 5.5 这条分界线是自动校验的

`client_term/`（终端客户端）没有碰撞体、没有 navmesh、没有骨骼、没有贴图、没有 UI 框架。因此：

> **如果一条规则在终端客户端里跑不出正确结果，它就已经漏到前端去了。**
>
> 反过来：**如果某个能力在终端客户端里根本没法存在**（骨骼动画、粒子），
> 那它就不该出现在 core 的任何接口里。

分界线因此不靠纪律维持，而是**有一个会报错的东西守着它**。
终端客户端不是省事的原型替代品，**是架构的一部分**——这也是 `DECISIONS` Q7 倾向文本原型的第二条理由。

⚠️ **待想透**：音频里的节日钟声、天气特效算 B 还是 C？
岛群调试台的「季相与水情」（积雪、植被枯荣、作物阶段、溪涧断流、漫滩、结冰、云海漫顶）
目前是在浏览器里按逐日天气推的、不改产物——到了游戏里，**作物阶段是 A 类（田块有真状态），其余看着像 B 类**，
但「溪涧断流」会不会影响取水点从而影响村的运转？若会，它就是 C 类。第十一节口径 n 连着这个问题。

## 六、facade 规格

三个词汇，只收发 POD + 字符串。**facade 先定，传输是第二层包装。**

### 6.1 intent —— 前端 → core，改变世界，进存档

语义级，不是坐标和按键：

```
{ "kind": "load_cargo",   "ship": 12, "item": "grain", "amount": 20, "unit": "local_dou" }
{ "kind": "set_sail",     "ship": 12, "to": 1592 }
{ "kind": "say",          "npc": 77,  "line": "promise_return" }
{ "kind": "place",        "entity": 301, "at": { "island": 5, "cell": 81234, "facing": 2 } }
{ "kind": "advance",      "days": 1 }
```

**每个 intent 带一个单调递增序号**，这就是重放的顺序。
core 返回接受或拒绝（拒绝带理由，供 UI 提示），**拒绝的 intent 不进存档**。

### 6.2 query —— 前端 → core，只读，不进存档

```
{ "kind": "can_place",  "entity": 301, "at": {...} }          → bool + 拒绝理由
{ "kind": "ledger",     "npc": 77, "observer": 1 }            → 渲染好的条目列表
{ "kind": "describe",   "item": 4412, "observer": 1 }         → { text, raw, unit, gloss, confidence }
{ "kind": "npc_at",     "npc": 77, "time": {...} }            → Placement
{ "kind": "route_cost", "from": 1165, "to": 1592, "mode": "trade" } → 天数 + 顺逆风差
```

⚠️ **query 一律带 `observer`。** 没有 observer 的查询等于绕过棱镜——
返回的是「上帝视角的真值」，而这个游戏里玩家永远不该拿到上帝视角（`docs/06` §三、D30）。
`observer: 1` 是玩家（`0` 是无效 id，见 `PLAN-ENTITY.md`）；调试工具可以传特殊值取真值，但**游戏前端不允许**（`CORE-render` 静态断言）。

### 6.3 patch —— core → 前端，状态变更通知

```
{ "entity": 77, "component": "placement", "fields": { "cell": 81240 } }
{ "event": "ledger_entry", "npc": 77, "rendered": "灯会那晚你答应会再来" }
{ "clock": { "year": 2, "day": 197 } }
```

前端照单全收，不推断、不补算。**patch 是 core 的独白，不是协商。**

### 6.4 边界纪律

- facade 头文件里**不得出现**任何 `zhouzhu_core` 内部类型——只有 POD 与字符串。
- facade 不得出现任何引擎类型（这是废话，但要有编译期断言兜住）。
- **facade 不得出现文件路径、句柄、流**（C5）。

## 七、空间模型

```cpp
struct Placement {
    uint16_t island;   // 岛号（或 船 / 地点 的特殊值）
    uint32_t cell;     // 格索引：100 m 岛屿网格，或 1 m 局部网格
    int16_t  ox, oy;   // 格内偏移，定点 1/256 格
    uint8_t  facing;   // 0–7，八向
    uint8_t  layer;    // 地面 / 局部网格 / 船内
};
```

更一般的位置类型是标签联合：
`AtPlace(place_id)` | `OnGrid(island, cell)` | `Aboard(ship, local_cell)` | `EnRoute(route, 已走天数)`。

| | 分辨率 | 谁管 | 进存档 |
|---|---|---|---|
| 岛屿网格 | 100 m，来自 generator | core 权威 | 是 |
| 地点局部网格 | 待定 0.5 或 1 m，只在主家 / 前哨 / 船内 | core 权威 | 是 |
| 连续坐标 | 浮点 | 前端 | **否** |

局部细网格只有玩家真正会建造和耕作的那几个地点需要，**数量是个位数**。
船本身就是一块会移动的局部网格。角色精确站位存「格 + 格内定点偏移」，重新加载站回格子中心即可。

## 八、两条流：intent 与事件

**这是两条不同的流，交接记录没说它们的关系，这里定下来。**

| | intent 流 | 事件日志 |
|---|---|---|
| 是什么 | 玩家意图：「装 20 斗谷上船」 | 世界里发生的事：「第2年197日，你答应铁匠会再来」 |
| 谁产生 | **只有玩家** | 玩家行为**和**世界钟（处境推进、改制、作物成熟、条目腐坏都没有对应 intent） |
| 进存档 | **是，它是真相** | 否，派生品，由重放重建 |
| 被谁读 | 重放 | fold 成态度 / 风评 / 处境状态 |
| 基数 | 一局几万条 | 一局几十万条 |

一个 intent 可以产生零个或多个事件；世界钟自己会产生大量没有 intent 对应的事件。

⚠️ **这个区分不定下来，`CORE-save` 根本没法验**——不知道该比对哪条流。

还连着两个未决：**事件类型表谁定**（口径 r）、**一件事发生了谁知道**（事件的可见性，就是风评的输入，口径 l）。

## 九、存档与重放

**存档 = 种子 + intent 流 + 周期快照。** 重放即得状态。白拿三样：

1. bug 可精确复现（贴一份存档就能复现）
2. 回归测试就是重放一段存档
3. `CORE-time` 可自动验证

**快照只是加载加速，不是真相。** 加载时找最近的快照，从那里重放剩下的 intent。

### 确定性三纪律（C++ 下必须主动守，这三个坑静默）

1. **不许遍历 `std::unordered_map` / `unordered_set`** —— 顺序是实现定义的，换编译器版本就变，
   不报错，只让重放悄悄分叉。用有序容器、排序后遍历、或自写稳定哈希表。**这是最可能出事的一条。**
2. **不许用 `<random>` 的分布** —— `uniform_int_distribution`、`shuffle` 跨标准库实现结果不同。
   自带 PCG 或 xoshiro，分布自己写几行。沿用 generator 的 `entity_rng(seed, stream, key)`。
3. **一切进存档的量用整数或定点** —— 载重、日期、户数、账本权重本来就该是整数；浮点只留表现层。

### slice 的确定性

⚠️ **slice 在一台机器上导出一次并提交进仓库，不要各机各导。**
同机重跑逐字节稳定，但 Windows 与 Linux 之间少数 float64 数组有极小差异（`check` 全过、`world.json` 一致）。
若两台机各导一份，地形栅格会微妙不同，`CORE-save` 的重放一致性会被**内容层面**的差异污染，这种 bug 极难定位。

⚠️ **generator 是 Python，别让 C++ 读 npz** —— Python 侧导出 JSON + 裸二进制栅格（带小 header），C++ 几十行读完。

## 十、`CORE-*` 校验（`apps/zhouzhu_check`，进 CI）

沿用 generator 的 `check` 纪律：硬项挂了就是红灯。

| id | 内容 | 硬 / 软 |
|---|---|---|
| `CORE-time` | 离场推进 30 天 == 在场逐日推进 30 天，派生状态逐字节相同 | 硬 |
| `CORE-fold` | 账本压缩前后，所有派生量（态度、欠与被欠、风评标签）不变 | 硬 |
| `CORE-render` | 静态断言：没有裸字面量的量 / 日期 / 物名进入 UI 层；没有不带 `observer` 的 query 被前端调用 | 硬 |
| `CORE-locale` | 切 locale 后既有契约、物品、节日日期全部重渲染，不留旧值 | 硬 |
| `CORE-save` | 存档往返 save→load→save 逐字节一致 | 硬 |
| `CORE-replay` | 同一条 intent 流重放两次，快照逐字节一致；跨编译器（MSVC / clang）也一致 | 硬 |
| `CORE-boundary` | facade 头文件不含内部类型与引擎类型；core 不含任何 IO 符号；`client_term` 能跑通全部 A 类能力 | 硬 |
| `CORE-content` | 加载时静态校验：谓词树引用的标签 / 字段 / NPC 全部存在 | 硬 |
| `CORE-layer` | L1 机制层的独立测试只 include L0、不含任何游戏概念即可跑通；源码扫描 `src/mech/` 不依赖 `src/rules/`（`PLAN-CLOCK` §二） | 硬 |

`CORE-fold` 不是形式主义：账本要压缩、条目要腐坏，若压缩改变 fold 结果，
**存档久了 NPC 会无缘无故性情突变**——这种 bug 半年后才暴露。

`CORE-boundary` 的最后一句是第 5.5 节那条自动校验的落地形式。

## 十三、风险

- **C 类漂移。** 分界线写得再清楚，写代码时仍会图省事在前端算一下。
  **靠 `CORE-boundary` 与 `client_term` 守**，不靠自觉。第 5.5 节那条是本稿最重要的一句话。
- **确定性纪律第 1 条。** `unordered_map` 遍历是 C++ 里最顺手的写法，也是最静默的坑。
  建议在 `zhouzhu_check` 里加一条源码扫描（grep 级别即可），别等 `CORE-replay` 在跨编译器时才炸。
- **intent 粒度失控。** 口径 k 把对话放进 core，intent 会变细。
  一旦有人开始往 intent 里塞鼠标位置，协议就被拖成帧同步了（C6）。
- **账本压缩改变 fold。** `CORE-fold` 要在**压缩策略写出来之前**就存在，否则会被事后迁就。
- **棱镜的性能。** 每个显示的量都过一次 render，列表翻页时是几百次。
  规模上没问题，但如果有人为此加缓存，`CORE-render` 的静态断言要能识破「缓存里存的是成品字符串」——
  **那正是禁令要禁的东西**。
- **slice 的口径漂移。** generator 那边改了产物格式，slice 就得重导。
  建议 slice 带 generator 的 `STAGE_VERSIONS` 与 seed，加载时对不上直接报错。
- **第三层的天气与季相。** 口径 n 的未想透项（5.5 末尾）会决定一批系统归 A 还是归 C，
  拖着不定，农事与取水点的设计会悬空。
