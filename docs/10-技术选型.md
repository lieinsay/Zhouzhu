# 10 · 技术选型

> **2026-09-19 重写。** 原版结论（Godot 4 + 2D 俯视 + GDScript）已被推翻，论据见下「为什么推翻了原版」。
> 旧结论进 `DECISIONS.md` 作废清单。本篇只记**选型与其理由**；设计稿见 `core/docs/PLAN-CORE.md` 及其下的各系统稿。

## 结论

**前后端分离。后端 `zhouzhu_core` 用 C++20，零引擎依赖；前端 3D，首个前端用 UE，但前端可换。**

```
zhouzhu_core   纯逻辑静态库。不 include 任何引擎、任何 IO、任何前端概念
      ↓
   facade      窄口：intent / query / patch 三个词汇，只收发 POD + 字符串
      ↓
 ┌────┴────┬──────────┬───────────┐
终端客户端   stdio 服务   GDExtension   UE plugin
(直接链)   (给工具用)   (进程内)     (进程内)
```

分离靠 **facade 的窄口**（编译期纪律）保证，**不靠进程边界**。进程边界只是纪律的一种强制执行手段，
需要时随时加（调试、崩溃隔离、做编辑器），不需要时省掉序列化。**facade 先定，传输是第二层包装。**

## 为什么推翻了原版

原版选 2D + Godot，核心论据是成本。**生成器做完之后，成本结构变了。**

| 原版论据 | 现在的实际情况 |
|---|---|
| 「3D 一个岛几天，2D 一个岛几小时」 | 那是**假设岛要手工做**。生成器现在给出 8000 个岛群的高程、地表、坡度、河湖、可耕地栅格与聚落点位，3D 地形近乎免费（heightmap → mesh，landcover → 散布，settlements.json → 摆房子），**比手画 2D tile 还便宜** |
| 「移动平台物理是经典噩梦」 | 后端根本不做物理（见「后端硬线」）。船是一块会移动的局部网格，位置是整数格 |
| 「空艇内部需处理层高、楼梯、碰撞」 | 同上。网格建造在后端是整数格 + 八向，层高是前端表现 |
| 「Godot 2D 是一等公民」 | 不再相关；且 Godot 会限制前端渲染能力，也会让后端代码高度依赖 Godot |

⚠️ **代价换了位置，没有消失。** 地形免费了，**角色建模、骨骼、动画、室内、可交互道具**在 3D 里是 2D 的几倍——
而这个游戏的重量偏偏全在人身上。常规解法是风格化（低面数、少量骨骼、不追面部表情、镜头不怼脸）。
**这条决定所有资产，待拍板（`DECISIONS.md` Q6）。**

## 后端：`zhouzhu_core`

### 语言与依赖

**C++20。** 理由不只是口味：UE 原生吃 C++，Godot 通过 GDExtension 也吃 C++，两边都能**进程内加载同一个 core**，
不付 IPC 税；发行是一个 dll/lib，不用打包解释器。

依赖清单只两行：`nlohmann/json`（单头）+ `doctest`（单头、编译快）。
沿用 generator「不引入 scipy/networkx/pandas」的纪律——**加新依赖要有理由**。

构建：CMake + MSVC 先跑 Windows，但从第一天保持 clang 能编（纯标准 C++，不用 MSVC 扩展）。

### 两条轴：引擎依赖，与底层 / 业务

**`zhouzhu_core` ≠ 底层。** 这个库里同时装着不会变的机制与会随设计改的业务规则，
它们一起受「零引擎依赖」约束，但**彼此之间还有第二道墙**：

```
L4  facade        intent / query / patch 窄口
L3  world         World 组装、intent 分派
L2  rules         账本 · 处境 · 田块 · 货舱 · locale 表的来源 · 文化特征表 …
L1  mech          时间 · 存储 · 日志 · 事件 · 空间 · 数值池 · 随机 · 渲染分派 · 场查询
L0  prim          Day · EntityId · 定点数
```

> **L1 不知道 L2 存在。** 它只认天、序号、句柄、整数 `kind`、整数格、整数量、位掩码。

**底层由「这是一台什么机器」决定，不由「这台机器现在跑什么内容」决定。**
所以数值池（伤害的底层形态）现在就建，哪怕首版不做战斗——
等战斗来了再设计它，它会在业务压力下诞生，一出生就长着「伤害类型」「护甲」这些业务概念。

两条轴各有一个会报错的东西守着：`CORE-boundary`（`client_term` 守引擎边界）、
`CORE-layer`（只 include L0 的独立测试 + 源码扫描守分层）。

### 四个原语

`09-首版切片.md` 与本篇原版各自列的「关键技术点」——存档体积、对白引用账本、时间线调度、文化表合并、第三幕世界改写——
**是同一件事的五个面**：

> 一条时间轴上不断追加的条目，加上一层把中性数据渲染成「某人在某时某地的理解」的表示层。

1. **世界钟** —— 全局唯一时钟（336 日 = 4 季 × 3 月 × 28 日，复用生成器历法）。
   作物、账本腐坏、处境时间线、风评传播、改制事件全是订阅者。**玩家不在场时照推。**
2. **只追加事件日志 + fold 出派生状态** —— 账本、处境、风评、改制共用一种存储：带日期的条目数组。
   当前关系 / 态度 / 风评是数组的 fold，**不落盘**。一个存储机制服务四个系统，压缩策略只写一次。
3. **棱镜渲染器** —— 量、日期、文字、物名在数据里中性（`{谷, 34, 本位斗}`、`{第2年, 第197日}`），
   显示时过 `render(值, 观察者, 地点, 时间)`，输出 `{text, raw, unit, gloss}`。
4. **文化场查询** —— `trait(特征, 地点) → 强度`，从连续场取值，不查地区表（铁律五 / D28）。
   生成器 `culture.py` / `probe trait` 已有实现，导出即可。

> ### 禁令
>
> **任何地方都不许把量、日期、地名、物名以成品字符串存下来或写进 UI。**
>
> 第三幕的官秤重校 / 文字统一 / 历法统一，在代码里就是**换一张 locale 表**。
> 第一天做对 = 三行配置；有一处 UI 写了字面量 = 第三幕要重写全部界面，
> 而那恰恰是整个项目要验证的东西（`09-首版切片.md` 的验证目标，D32）。

### 后端是权威，前端是哑终端

- 后端持全部状态与时钟；前端只持表现状态（镜头、动画进度）。
- **时钟归后端。** 前端发 `set_speed` / `advance`，自己不跑表，否则两边必漂。
- **棱镜渲染在后端**（最要紧）。前端可以只用返回的 `text`，但**没有办法绕过棱镜**。换引擎时第三幕机制一行不用重写。
- **intent 是语义级的**：「装 20 斗谷上船」「对铁匠说这句」「起航去 1592」，不是坐标和按键。
- **逐帧的东西不过边界**：走路、镜头、粒子全留前端。这条不早定，协议会被拖成帧同步。

### 后端硬线：不许有「速度」和「碰撞」

只有「在哪个格」和「什么时候到哪个格」。NPC 日程是「辰时在铺子，午时在码头」，
**中间那段路由前端补间**，后端不跑他的脚步。后端也**不做寻路**——只有一张预计算好的地点间成本图
（生成器连顺逆风的航线成本都算好了）。

理由：一旦后端开始算速度和碰撞，它会慢慢长成一个又慢又不准的物理引擎，而且重放立刻失效。

## 空间模型：整数，不用浮点 transform

```cpp
struct Placement {
    uint16_t island;   // 岛号（或 船 / 地点 的特殊值）
    uint32_t cell;     // 格索引：100 m 岛屿网格，或 1 m 局部网格
    int16_t  ox, oy;   // 格内偏移，定点 1/256 格
    uint8_t  facing;   // 0–7，八向
    uint8_t  layer;    // 地面 / 局部网格 / 船内
};
```

12 字节，全整数，重放精确。前端转 `FTransform` 是一行。
更一般的位置类型是标签联合：`AtPlace(place_id)` | `OnGrid(island, cell)` | `Aboard(ship, local_cell)` | `EnRoute(route, 已走天数)`。

**离散八向是更优解，不是妥协**：`07-核心循环.md` 要的是网格建造——不会想把一张床摆成 37.4°。
缩放后端根本不需要（那是美术的事）。

| | 分辨率 | 谁管 | 进存档 |
|---|---|---|---|
| 岛屿网格 | 100 m，来自 generator | 后端权威 | 是 |
| 地点局部网格 | 0.5–1 m，只在主家 / 前哨 / 船内 | 后端权威 | 是 |
| 连续坐标 | 浮点 | 前端 | **否** |

局部细网格是必须的：`07-核心循环.md` 的空艇网格建造与主家装修活在这一层（船本身就是一块会移动的局部网格）。
只有玩家真正会建造和耕作的那几个地点需要，数量是个位数。
角色精确站位存「格 + 格内定点偏移」，重新加载站回格子中心即可。
**取 0.5 m 还是 1 m 待拍板**（见 `core/docs/PLAN-CORE.md` 口径表）。

格上的**占用与通行**（碰撞的离散版）是一个独立的底层系统，见 `core/docs/PLAN-SPACE.md`：
后端不做连续物理，但「这格能不能进、这东西能不能摆、船体还连不连通」必须由后端权威回答。

## 实体模型：组合式，抄形不抄 UE 的类型

| 实体 | 组件 |
|---|---|
| NPC | Placement · Ledger · Predicament · Schedule |
| 村 | Placement · Population · Locale |
| 船 | Placement · Cargo · GridBuild |
| 田块 | Placement · Field |
| 玩家 | Placement · Ledger · Cargo · Knowledge |

存储不必花哨：每种组件一个 `vector` + 一个稀疏索引数组，遍历顺序就是数组顺序，**天然确定**。

前端照常：一个后端实体 → 一个 `AActor`，后端组件 → 对应的 `UActorComponent`，中间一层薄映射（几百行，机械的）。
**同一个模型，两套类型，一层转换**；换引擎时换那一层，core 一行不动。

**`UObject` / `AActor` / `FVector` 不得进 core**：它们依赖 UHT 代码生成与 UE 的 GC，在 UE 之外编译不了——
`zhouzhu_check` 与单测要拉整个 UE 才能跑（CI 从几秒变几十分钟）、终端客户端没了、改一行规则要走 UBT。
而且「不想依赖 Godot」换成「依赖 UE」是同一种病换名字。

## 确定性三纪律

存档做成「种子 + intent 流 + 周期快照」，**确定性是硬要求**。C++ 里这三个坑**静默**，埋进去半年后才炸：

1. **不许遍历 `std::unordered_map` / `unordered_set`** —— 顺序是实现定义的，换编译器版本就变，
   不报错，只让重放悄悄分叉。用有序容器、排序后遍历、或自写稳定哈希表。**这是最可能出事的一条。**
2. **不许用 `<random>` 的分布** —— `std::uniform_int_distribution`、`shuffle` 跨标准库实现结果不同（MSVC vs libstdc++）。
   自带 PCG 或 xoshiro，分布自己写几行。沿用 generator 的 `entity_rng(seed, stream, key)` 习惯。
3. **一切进存档的量用整数或定点** —— 载重、日期、户数、账本权重本来就该是整数；浮点只留表现层。

后端确定性 → 重放即得状态。白拿三样：bug 可精确复现、回归测试就是重放一段存档、`CORE-time` 可自动验证。
**快照只是加载加速，不是真相。**

## 数据驱动：从「最好这样」升级为「不这样就做不下去」

原版说「核心资产是几张表，不是代码」——在 GDScript 下那是个好习惯，在 C++ 下**是生存条件**（改内容要重编译）。

- **数值与表**（文化主表、偏移量、微差、九格表、NPC、物产）：全外置 JSON，**运行时热重载**。
- **内容侧逻辑**（事件触发条件、对白分支、处境时间线判据）：倾向 **JSON 谓词树**（约两三百行），而非嵌 Lua。
  谓词树能在加载时静态校验「这条微差引用的标签存在吗」，是 generator `check` 纪律的延续。
  嵌 Lua 的缺点：多一个依赖、确定性要额外守、错误在运行时才炸。**未最终拍板。**

### 关于「C++ 没有反射」

不是顾虑。记录在此以免重复讨论：

| 用途 | 没反射会怎样 | 做法 |
|---|---|---|
| 存档序列化 | 加字段要改两处，漏了静默丢字段 | `NLOHMANN_DEFINE_TYPE_INTRUSIVE` + round-trip 测试兜底 + 存档版本号 |
| 调试面板 / 状态查看器 | 要给每类型手写 dump | **不用写**——状态本来就过 JSON，面板直接吃序列化结果。**序列化就是穷人的反射** |
| 谓词树引用字段 | 要手写「字段名 → 取值函数」注册表 | 几十行显式注册表；让拼错字段名变成**加载时报错**，缺点转优点 |

真正担心的只有「改内容要重编译」一条，已被内容外置解决。
确定性三纪律不是「C++ 缺功能」，是「C++ 不替你挡」——Python 的 `set` 遍历顺序同样不保证，只是在 generator 里已经形成习惯了。
C++26 静态反射（P2996）已进标准但编译器支持还早，别指望；真烦了再考虑 `boost::pfr`。

## CORE-\* 校验（沿用 generator 的 check 纪律）

| id | 内容 |
|---|---|
| `CORE-time` | 离场推进 30 天 == 在场逐日推进 30 天，派生状态逐字节相同 |
| `CORE-fold` | 账本压缩前后，所有派生量（态度、欠与被欠、风评标签）不变 |
| `CORE-render` | 静态断言：没有裸字面量的量 / 日期 / 物名进入 UI 层 |
| `CORE-locale` | 切 locale 后既有契约、物品、节日日期全部重渲染，不留旧值 |
| `CORE-save` | 存档往返 save→load→save 逐字节一致 |
| `CORE-replay` | 同一条 intent 流重放两次快照一致；跨编译器（MSVC / clang）也一致 |
| `CORE-boundary` | **守引擎边界**：facade 不含内部类型与引擎类型；core 不含任何 IO 符号；`client_term` 能跑通全部 core 侧能力 |
| `CORE-layer` | **守分层**：L1 的独立测试只 include L0、不含任何游戏概念即可跑通；源码扫描 `src/mech/` 不依赖 `src/rules/` |
| `CORE-content` | 加载时静态校验：谓词树引用的标签 / 字段 / NPC 全部存在 |

各底层系统另有自己的校验（`CLK-*` / `ENT-*` / `SPC-*` / `POOL-*`），见各系统设计稿。

`CORE-fold` 不是形式主义：账本要压缩、条目要腐坏，若压缩改变 fold 结果，存档久了 NPC 会无缘无故性情突变——
这种 bug 半年后才暴露。

## 不为性能做任何设计

状态规模：几百个 NPC、几千条账本条目、两个邦。`std::vector<T>` + 整数 id 够到天荒地老。
**不上 ECS，不做对象池，不用模板元编程。**（组合式建模不是 ECS，见上。）
省下的复杂度换成「状态是平的、存档是直的、重放是准的」。

同理，**一开始不上 gRPC / protobuf**：schema 还在大改，JSON over stdio 够用（单人游戏每次几 KB），嫌慢再换 MessagePack。

## 与生成器的接口：slice

从 seed42 挑**两个真实节点**导出：地形与聚落、逐日天气、人口与政治、两地间航线成本与顺逆风差、两份九格表。

⚠️ **generator 是 Python，别让 C++ 读 npz** —— Python 侧导出 JSON + 裸二进制栅格（带小 header），C++ 几十行读完。

⚠️ **slice 在一台机器上导出一次并提交进仓库，不要各机各导。** 同机重跑逐字节稳定，
但 Windows 与 Linux 之间少数 float64 数组有极小差异（`check` 全过、`world.json` 一致）。
若两台机各导一份，地形栅格会微妙不同，`CORE-save` 的重放一致性会被**内容层面**的差异污染，而这种 bug 极难定位。

## 两个判据

**「底层活了」** —— 在一个**没有任何游戏概念**的测试里跑通：

> 造一个钟、一张格、几个池、一本日志 → 推进一千天 → 排期级联与取消 →
> 往格上放东西、判占用与连通 → 对池做一串带来源的增减 → 压缩日志、fold 不变 →
> 存档往返逐字节一致 → 换个编译器重放，结果一样

**「业务活了」** —— 在终端客户端里一口气跑通：

> 装货起航 → 过 9 天 → 到邻邦 → 和铁匠说话，她提起你上次答应会再来 →
> 第三幕开关一拨 → 同一袋谷的显示从「三石七斗」变成官定说法，括号里的换算消失

这一串通了，四个原语全部被证明，后面三幕基本是配置和内容。

**底层活了要先于业务活了。** 反过来做，底层就是从业务里刮出来的，一定是脏的。

## 低成本玩法验证路径
