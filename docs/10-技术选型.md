# 10 · 技术选型

## 结论

**Godot 4 + 2D 俯视（45° 斜视角），双视角结构。**

## 2D vs 3D

**选 2D。**

| | 2D 俯视 | 3D |
|---|---|---|
| 空艇内部布局 | 网格建造，直观 | 需处理层高、楼梯、碰撞，工作量 ×5 |
| 移动平台上的角色 | 父子坐标即可 | 移动平台物理是经典噩梦 |
| 岛屿数量 | 一个岛几小时 | 一个岛几天 |
| 美术成本 | 可控（像素 / 手绘） | 建模+贴图+动画，小团队几乎不可能 |

3D 唯一优势是「飞行的空间感」。可用 **2D 俯视 + 分层高度**（云层、岛屿投影、视差滚动）
拿到 80% 的飞行感，成本 1/10。

**而且本作的重量在人与社会，不在飞行奇观。** 2D 更贴合定位。

## 双视角结构

- **航行视角**：简化的 2D 俯视航行界面。云层、气流、航线、遭遇。
- **地面视角**：登岛后切换为正常 2D 场景。种地、建造、对话。

## 引擎

**Godot 4（首选）**
- 2D 是一等公民，不是在 3D 上模拟 2D
- TileMap、Y-sort、2D 光照开箱即用
- 节点 / 场景系统天然适合「每个岛 = 一个场景」的分块内容
- 开源免费，无授权风险，导出体积小
- 缺点：3D 相对弱（本项目不需要）；第三方资源少于 Unity

**备选：Unity** —— 若需成熟插件生态或考虑主机移植；C# 也更接近 Java。
**排除：虚幻** —— 2D 项目上是负资产。

## 语言

GDScript 起步（迭代快，适合原型），性能热点可后续用 C# 或 GDExtension。
**本项目的瓶颈在设计与内容，不在性能。**

## 数据驱动是硬要求

本作的核心资产是几张表，不是代码：

- 文化主表 + 各地偏移量
- 行为标签与价值解读矩阵
- 人情账本的条目类型与权重
- NPC 处境时间线
- 地区九格表（见 `08`）

**这些必须做成外部资源文件（JSON / Godot Resource），可热改、可批量编辑。**
如果它们被写死在代码里，这个项目就做不下去了。

## 低成本玩法验证路径（可选）

开发者已有 Fabric 1.21.1 空岛模组（`D:\Project\My\SkyIsland`）。
可先在 Minecraft 里做模组原型，验证**系统手感**——航行、载重、岛屿差异化、破城取舍。

> 注意：模组原型验证不了**文化棱镜与人情账本的情感效果**。
> 后者仍需在正式原型中做，而那恰恰是本作的命门。

## 关键技术点（早期确认）

1. **人情账本的存档体积** —— 事件数组的归并/压缩策略
2. **对白引用账本条目** —— 模板/插槽机制
3. **处境时间线调度** —— 日期驱动的事件队列，离场时也推进
4. **文化表的合并规则** —— 主表 + 偏移量的覆写与继承
5. **第三幕的"世界改写"** —— 度量、文字、历法的统一必须能**批量改写既有内容**
   （所有 UI 显示的秤、所有契约文本、所有节日日期）。这在架构上要早做准备。
