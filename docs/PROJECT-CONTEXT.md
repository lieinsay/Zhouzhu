## 数据与成因

用户本次重申：数据必须合理、真实，制作或修改前需要合理理由，不能乱造。

生成器 `CLAUDE.md` 的原有原则是：“原理定了以合理为主，要硬凑才对得上就改原理；地球的数只当参照。”后续修改需要交代来源、单位、尺度、适用条件和守恒约束。目标画面只能用来提出需求，不能反过来充当物理系数的证据。

生成器先完成数据规则，游戏随后读取。源数据没有提供的形态或过程需要标明缺口。当前河网契约、常驻/临时供水、米制与已知限制见 [RIVER-DATA.md](RIVER-DATA.md)。生成器算法在 C++ `core/`，Python 是入口与产物工具；相关决策见子模块的 `docs/DESIGN-NOTES.md`、`docs/DATA-GUIDE.md` 与 `docs/spec/13-浮石与陆地的生灭.md`。

2026-10-05 用户确认河网尺度目标：小溪、支流、干流的总体宽深合理提高，同时存在宽浅段、深潭等局部变化，两者不冲突。自然形态变化不能代替总体尺度目标；只完成水账或断面修复也不能宣称加宽完成。允许研究有依据的供水与地貌调整，不以既有公式或气候假设排除方案；世界设定的实质调整应带具体依据与影响一起讨论。20–40 m 仍只是曾提出的视觉期望，不是硬指标。

## 开发与验证

- 用中文沟通；Zhouzhu 常规工作直接在 main 完成。按独立主题暂存和提交，只包含本次工作；提交已获长期授权，推送没有。
- 先生成器、后游戏地形地貌。用户要可复用的生成工具，避免只对某个场景手摆物件修效果。
- 减少游戏启动，端到端检查以无头、顺序为主。开可见窗口先确认，用户关闭不重开。截图使用实际开局日期和真实时序，不能只挑固定大流量证明成功。
- 性能结论要区分 Debug 与 Release；旧记忆中的帧耗只说明当时版本，不直接视为当前瓶颈。
- 现有编译配置以 [BUILD-RIDER.md](BUILD-RIDER.md) 和 `.run/zhouzhu.run.xml` 为准。调试真正的 Godot 可执行文件，不能把 `_console.exe` 启动壳当作扩展宿主。MSVC 依赖前缀按实际日志与 Ninja 配置核对，不照抄旧语言设置。
- C++ 中文字符串同时核对 `/utf-8` 与 Godot 字符串构造；非 ASCII 字面量使用 `U"..."` 或明确的 UTF-8 转换。乱码先检查字节，不能单凭终端显示改代码。
- 玩法里的短途搬运交给人，长途物流交给船、车辆或设施。自动测试同样不能以公里级抱货步行为正常流程。
- 完成实际功能后更新 FeatureMap，已有功能节点复用，不把尚未解决的问题写成完成。
