# 舟渚·内容工坊

内容工坊是给开发人员使用的本地网页工具，独立于 Godot。它从当前仓库的 C++ 内容表建立只读基线，以草稿管理新增和修改，让配方、物品及相关设施可以一起审阅。草稿不会被游戏读取；工具不修改游戏的源码、资产、存档或运行配置。

## 启动

在 Zhouzhu 项目根目录运行：

```powershell
node tools/content-studio/server.mjs
```

需要 Node.js 24，服务和测试使用 Node 内置库，无 npm 安装步骤。访问 <http://127.0.0.1:4176>。服务只绑定 `127.0.0.1`，启动不需要编译 C++ 或运行游戏；按 `Ctrl+C` 结束服务。

工具源码放在 `tools/content-studio/`。当前随主仓库管理；没有独立远端仓库时，不创建只能在本机克隆的子模块 URL。以后若要独立维护，可在有可访问远端和版本发布约定后抽出子模块。

## 编辑流程

1. 浏览当前内容。条目来自真实源码，工具保留基线来源信息。
2. 选条目编辑，或新建、复制一个条目。修改先停留在页面，再保存为工具草稿。
3. 在「变更审阅」核对新增、修改、移除，在「内容校验」检查引用与约束。新增配方前，先确保材料与产物的物品 ID 存在。
4. 导出 JSON 留作备份或交给其他开发人员审阅；导入确认后替换整份工具草稿，先核对差异并保留原草稿的导出备份。导出的文件可以原样再导入。
5. 下载源码建议供开发人员审阅。需要接入游戏时，另行安排源码修改和游戏验证；工具不会自动应用建议。

建议第一次体验只改一条已有配方，例如把木板配方的单次产出从 4 调为另一正整数。查看批次估算与变更清单，导出草稿，再关闭工具；游戏的 `src/recipes.cpp` 不会被改写。

`Ctrl+S` 保存草稿；`Ctrl+K` 聚焦搜索，非输入框中也可按 `/`。存在内容校验错误的草稿仍可保存以便继续整理；结构不合法的 JSON 会被拒绝，不会覆盖已有草稿。

## 管理范围与来源

| 页面 | 管理内容 | 当前基线入口与边界 |
| --- | --- | --- |
| 道具目录 | 物品 ID、中文名称、叠放上限、图标色 | `src/crops.cpp` 的物品表 |
| 资源与采集 | 采集资源定义、物品对应关系与采集参数 | `src/deposit_kinds.cpp` 的资源种类表；不生成岛群矿藏位置、品位或存量数据 |
| 合成配方 | 配方 ID、产物、单次产出、工作站、材料清单 | `src/recipes.cpp` 的 `RecipeDef` 表；一条配方至多 3 种材料 |
| 机械与设施 | 可放置物件的尺寸、外观类别、容器格数、工作站及照明范围 | `src/placeables.cpp` 的 `PropDef` 表；当前游戏已有工作台、窑、木箱、火把、篱笆，不把尚无实现的机械假称为游戏现有能力 |
| 建筑外壳 | 名称、尺寸、层数与房屋属性 | `src/buildings.cpp` 的建筑外壳表；不编辑室内模板或世界中房屋的位置 |
| 搭建构件 | 构件的物品、角色、槽位、材质 | `src/build_pieces.cpp` 的 `PieceDef` 表 |
| 船舶拓展 | ID、名称、占格尺寸、质量、推力、船舱与放置限制 | `src/ship_layout.cpp` 的 `ModuleDef` 表；管理种类定义，不改玩家船布局或存档 |
| 作物定义 | 种子、产物、生长期倍率、产量 | `src/crops.cpp` 的 `CropDef` 表 |
| 采集工具 | 工具物品、适用采集产物、速度倍率 | `src/crops.cpp` 的 `ToolDef` 表 |
| 散布采集物 | 采集产物、耗时、产量、再生时间、外观与碰撞半径 | `src/deposit_kinds.cpp` 的 `ScatterKind` 表 |
| 变更审阅 | 与当前基线的差异、还原和重置 | 只审阅工具草稿，不执行游戏编译或修改源码 |
| 内容校验 | 数据约束、跨表引用、制作可达性与源码漂移 | 根据当前源定义检查；运行行为仍需以后接入时验证 |

草稿中的新 ID 只是内容方案。涉及新的外观枚举、行为、工作站种类或建筑角色，仍需要 C++ 实现；导出数据不等于已经开发出对应的游戏功能。资源分布的成因、地图几何及生成器契约继续按原有项目流程处理。

## 合成配方

产物和每项材料都用物品 ID 引用物品表。配方 ID 与产物 ID 分开：同一产物可以有多种制作方式，例如 `torch` 和 `torch_firewood` 都产出火把。编辑时应保留不同制作方式各自的 ID。

材料数量与单次产出必须为正整数，材料种类至多 3 项，与当前游戏 `RecipeDef::in[3]` 一致。工作站使用当前游戏已有的 `HAND`（随身）、`WORKBENCH`（工作台）、`KILN`（窑）。工作台、窑等设施的定义与配方相互引用，删除相关条目时应查看引用检查。

制作链帮助查找材料来源和配方关系。同一材料有多种做法时，只展开当前清单中的第一条配方，并标明替代方案数量；这条参考链不表示唯一方案。链中出现循环时，要结合「内容校验」判断是否能从采集、作物或其他配方获得该物品。内容校验会考虑替代配方及工作站是否可制作、可放置，无法达成的闭环或缺失引用需要修正。

批次物料估算按选定配方的单次材料和产出乘以批次数，只计算这条配方的直接用料，不自动替开发人员选取上游替代配方。它不模拟玩家背包格数、堆叠腾挪、鼠标拖动堆、设施距离、采集时间或实际合成成功与否；游戏的这些行为仍由 `recipes::craft`、`ItemSlots` 与场景逻辑决定。

条目的 JSON 定义可供核对导入结果及字段原值。建筑外壳不是背包物品，不能直接当作配方产物；船模块的质量和推力是当前游戏抽象值，不标作公斤或牛顿。

## 保存、导入导出与冲突

持久化草稿保存在 `tools/content-studio/workspace/draft.json`，重置时的备份也写在这个工作目录，目录被 Git 忽略。文件封装包含版本、保存时间与校验指纹，不宜手工覆盖；请使用页面的 JSON 导入、导出。导出是可移动的完整草稿备份，可原样再导入；需要团队审阅时，把导出文件放到明确约定的位置另行提交，避免把本机工作区混进游戏内容提交。

保存采用版本检查。两个浏览器页面同时编辑时，较旧页面不能覆盖较新保存，服务返回 HTTP `409` 冲突；先导出旧页面中需要保留的内容，再读取最新草稿并合并。

草稿同时记录其源码基线的 hash。读取基线的 C++ 文件发生变化后，旧草稿会报告源码漂移，服务拒绝保存；不能把旧条目的整表替换误当作基于新源码的编辑。漂移的草稿仍可查看、导出和审阅差异。先导出保全草稿、核对当前源码和差异，再在「变更审阅 → 重置全部草稿」确认重置：工具先将旧文件备份为 `workspace/draft.backup.<UUID>.json`，随后立即保存基于当前源码的新草稿。要保留的编辑需逐项重新整理，旧导出文件不会被自动合并进新基线。

重置会放弃页面上尚未保存的编辑，因此重置前也要导出页面中的草稿保全。工具不自动重设旧草稿的基线，不自动合并源码变更。HTTP `409` 是冲突提示，不表示已有游戏内容或草稿被删除。

## 隔离与后续接入

游戏没有新增输入、菜单、autoload 或内容加载路径，CMake 和 Godot 项目没有工具依赖。`src/dev_manual.cpp` 只在文件顶部注释给出本工具文档与启动命令；`test_dev_manual` 对这个文档入口作一致性校验。

工具是管理与设计工作区，当前没有「应用到游戏」操作。未来接入应先明确内容文件格式、迁移和旧存档规则，把经审阅的草稿转换成正式数据或源码变更，再执行与改动相符的 C++、游戏和导出验证。不得靠工具擅自为生成器补造资源或地貌数据。
