# 舟渚·内容工坊

内容工坊是给开发人员使用的本地网页工具，独立于 Godot。它从当前仓库的 C++ 内容表建立只读基线，以草稿管理新增和修改，让配方、物品及相关设施可以一起审阅。内容草稿不会被游戏读取。2026-10-26 新增独立正式美术入口，只有该入口会写入游戏美术绑定，不修改源码、数值、存档或运行配置。

## 正式美术资源与应用

2026-10-27 场景补齐批次使用独立工作空间 `workspace/scene-art-20261027` 和回环端口4178，保留原有内容/美术草稿。表面定义在 `game/art/scene-slots.json`，新增材质仍通过同一正式登记和独立应用。真实开局读取检查为 `res://tests/scene_materials_e2e.tscn`；完整执行与验收见 `docs/art-assets/SCENE-COMPLETION-20261027.md`。木构件采用逐构件米制UV，梁端单次映射端纹；没有该属性的原生网格保留三平面回退。

启动后进入 <http://127.0.0.1:4176/art.html>（主页右上角「正式美术资源」）。查看各命名空间身份、版本、来源、SHA、提示词、代理审图与用户逐项确认状态；选择版本 →「暂存美术绑定」→「应用美术到游戏」。暂存保存在独立 `workspace/art-draft.json`，不读取 `draft.json` 或 `project.visuals`。应用校验原图/派生指纹和代理审图结果，检查并发版本，原子更新 `game/art/bindings.json`，并保存 `assets/art/applications/` 前后快照。

游戏重新启动后从 `res://art/bindings.json` 读取正式图片，背包、快捷栏、木箱/船舱、拖拽物品、配方产物与材料共用 `item.<id>`。工具默认使用同一已应用版本；既有显式 `project.visuals` 工具草稿仍保留，可在正式资源页核对游戏实际应用。缺图继续颜色/名称回退，数量、快捷键、选择态和提示文字独立绘制。这里只应用美术，不顺带应用配方、经济、模型变换或其他草稿。

制作入口：`python tools/art-assets.py --help`。`register` 非覆盖登记原图并生成统一 256 方图；`sheet` 输出明暗底32/48/64像素审图表；`review` 分别记录代理通过/拒绝。原图与旧 v1 均保留，内置生图提示词和参考指纹进入正式登记。制作脚本需要 Pillow；`register-material` 非覆盖登记受控基础色版本并计算线性色均值，铁自动限定为样件。工坊服务不新增第三方依赖。规范见 [ART-DIRECTION.md](ART-DIRECTION.md)。

真实模型预览：`python tools/art-preview/render.py --help`。先用已有模型导出器把本次真实模型快照写入新版本目录；家具导出命令为 `node tools/art-preview/export-furniture.mjs --output <新的版本目录>`，由 `tools/art-preview/furniture-export.cpp` 在独立MSVC构建中直接调用 `furniture_parts` / `mesh_kit`。渲染器需要numpy与Pillow，统一正交相机、柔光和透明背景，不改变米制尺寸、几何或原颜色。`--model-directory` 与 `--furniture-directory` 指定已核对来源；用 `--version vN` 增加版本，拒绝覆盖已登记版本。正式资源页可按物品、船模块、建筑、家具筛选；模块与建筑目录、游戏改装卡片、建筑面板、室内当前家具工具使用同一正式预览。当前模型的精绘造型/材质缺口见 `docs/art-assets/model-gaps.json`；代理仅确认快照预览准确，不将其当作风格化模型完成。

## 启动

在 Zhouzhu 项目根目录运行：

```powershell
python tools/content-studio/server.py
```

需要 Python 3.10 或更新版本（已验证 3.12），服务和后端测试仅使用标准库，无需 pip 安装。访问 <http://127.0.0.1:4176>。服务只绑定 `127.0.0.1`，启动不需要编译 C++ 或运行游戏；按 `Ctrl+C` 结束服务。

工具源码放在 `tools/content-studio/`。当前随主仓库管理；没有独立远端仓库时，不创建只能在本机克隆的子模块 URL。以后若要独立维护，可在有可访问远端和版本发布约定后抽出子模块。

2026-10-13 用户授权增加本机 Work VPN 地址 `10.8.0.2` 的入口，并明确允许 `10.8.0.0/24` 客户端访问。运行以下命令会同时绑定 `127.0.0.1:4176` 和 `10.8.0.2:4176`：

```powershell
python tools/content-studio/server.py --network-address 10.8.0.2 --allow-network 10.8.0.0/24
```

网络地址必须是当前本机已有的非回环 IPv4，不接受 `0.0.0.0` 或主机名。网络入口读取和写入都限定客户端来源网段；本机入口保留。两个 HTTP 监听器共用工作空间和保存队列，Host 仅允许明确入口地址，写入仍要求 Origin 与所访问入口相同，不跨入口放宽同源限制。默认命令不开放网络访问。Windows 防火墙需要为 Python 放行 TCP 4176，限定本机 `10.8.0.2`、远端 `10.8.0.0/24`；已有其他端口的 Python 规则不覆盖此入口。

## 编辑流程

1. 浏览当前内容。条目来自真实源码，工具保留基线来源信息。
2. 选条目编辑，或新建、复制一个条目。修改先停留在页面，再保存为工具草稿。
3. 在「变更审阅」核对新增、修改、移除，在「内容校验」检查引用与约束。新增配方前，先确保材料与产物的物品 ID 存在。
4. 导出 JSON 留作备份或交给其他开发人员审阅；导入确认后替换整份工具草稿，先核对差异并保留原草稿的导出备份。导出的文件可以原样再导入。
5. 下载源码建议供开发人员审阅。需要接入游戏时，另行安排源码修改和游戏验证；工具不会自动应用建议。

建议第一次体验只改一条已有配方，例如把木板配方的单次产出从 4 调为另一正整数。查看批次估算与变更清单，导出草稿，再关闭工具；游戏的 `src/recipes.cpp` 不会被改写。

`Ctrl+S` 保存草稿；`Ctrl+K` 聚焦搜索，非输入框中也可按 `/`。存在内容校验错误的草稿仍可保存以便继续整理；结构不合法的 JSON 会被拒绝，不会覆盖已有草稿。

## 管理范围与来源

| 页面 | 管理内容 | 当前基线入口与边界 |
| --- | --- | --- |
| 道具目录 | 物品 ID、中文名称、叠放上限、图标色 | `src/crops.cpp` 的物品表 |
| 资源与采集 | 采集资源定义、物品对应关系与采集参数 | `src/deposit_kinds.cpp` 的资源种类表；不生成岛群矿藏位置、品位或存量数据 |
| 合成配方 | 配方 ID、产物、单次产出、工作站、材料清单 | `src/recipes.cpp` 的 `RecipeDef` 表；一条配方至多 3 种材料 |
| 机械与设施 | 可放置物件的尺寸、外观类别、容器格数、工作站及照明范围 | `src/placeables.cpp` 的 `PropDef` 表；当前游戏已有工作台、窑、木箱、火把、篱笆，不把尚无实现的机械假称为游戏现有能力 |
| 建筑外壳 | 名称、尺寸、层数与房屋属性 | `src/buildings.cpp` 的建筑外壳表；不编辑室内模板或世界中房屋的位置 |
| 搭建构件 | 构件的物品、角色、槽位、材质 | `src/build_pieces.cpp` 的 `PieceDef` 表 |
| 船舶拓展 | ID、名称、占格尺寸、质量、推力、船舱与放置限制 | `src/ship_layout.cpp` 的 `ModuleDef` 表；管理种类定义，不改玩家船布局或存档 |
| 作物定义 | 种子、产物、生长期倍率、产量 | `src/crops.cpp` 的 `CropDef` 表 |
| 采集工具 | 工具物品、适用采集产物、速度倍率 | `src/crops.cpp` 的 `ToolDef` 表 |
| 散布采集物 | 采集产物、耗时、产量、再生时间、外观与碰撞半径 | `src/deposit_kinds.cpp` 的 `ScatterKind` 表 |
| 变更审阅 | 与当前基线的差异、还原和重置 | 只审阅工具草稿，不执行游戏编译或修改源码 |
| 内容校验 | 数据约束、跨表引用、制作可达性与源码漂移 | 根据当前源定义检查；运行行为仍需以后接入时验证 |

草稿中的新 ID 只是内容方案。涉及新的外观枚举、行为、工作站种类或建筑角色，仍需要 C++ 实现；导出数据不等于已经开发出对应的游戏功能。资源分布的成因、地图几何及生成器契约继续按原有项目流程处理。

## 合成配方

产物和每项材料都用物品 ID 引用物品表。配方 ID 与产物 ID 分开：同一产物可以有多种制作方式，例如 `torch` 和 `torch_firewood` 都产出火把。编辑时应保留不同制作方式各自的 ID。

材料数量与单次产出必须为正整数，材料种类至多 3 项，与当前游戏 `RecipeDef::in[3]` 一致。工作站使用当前游戏已有的 `HAND`（随身）、`WORKBENCH`（工作台）、`KILN`（窑）。工作台、窑等设施的定义与配方相互引用，删除相关条目时应查看引用检查。

制作链帮助查找材料来源和配方关系。同一材料有多种做法时，只展开当前清单中的第一条配方，并标明替代方案数量；这条参考链不表示唯一方案。链中出现循环时，要结合「内容校验」判断是否能从采集、作物或其他配方获得该物品。内容校验会考虑替代配方及工作站是否可制作、可放置，无法达成的闭环或缺失引用需要修正。

批次物料估算按选定配方的单次材料和产出乘以批次数，只计算这条配方的直接用料，不自动替开发人员选取上游替代配方。它不模拟玩家背包格数、堆叠腾挪、鼠标拖动堆、设施距离、采集时间或实际合成成功与否；游戏的这些行为仍由 `recipes::craft`、`ItemSlots` 与场景逻辑决定。

条目的 JSON 定义可供核对导入结果及字段原值。建筑外壳不是背包物品，不能直接当作配方产物；船模块的质量和推力是当前游戏抽象值，不标作公斤或牛顿。

## 缩略图与模型

场景材质小样验收：使用原Godot运行 `res://tests/art_material_e2e.tscn`，无头检查绑定与参数；经授权打开可见窗口时输出近景、反向光、湿润输入和远景截图。它使用正式 `ArtSurface` / `curved_material::surface` 和同一生产着色器，不加载世界、不改生成器或世界天气数据。木材0.5m、夯土1m、陶土0.5m、铁0.5m，仅基础色；原粗糙度与明确金属度仍为标量。局部三平面映射与纹理mipmap处理接缝及远景。首轮仅把木楼板、夯土墙、陶土表面映射到SharedLooks；铁仅在受控样件验证。木梁与家具逐构件纹理方向、完整材质通道及其他表面仍待后续，不扩成全套PBR任务。

「道具目录 → 缩略图库」展示每个当前道具分别使用内置 ImageGen 生成的透明背景 PNG。提示词和最终原图指纹保存在工具 `assets-source/prompts-*.json`，原图位于 `public/assets/thumbnails/<id>-v1.png`；图像未编辑、裁切或缩放，只作为工具的设计缩略图，不代表对应的游戏网格。道具清单、配方材料和产物都优先使用这些缩略图，恢复颜色显示只用于没有绑定图像的内容。

「外观与模型」提供三维预览、模型绑定、XYZ 缩放、旋转和偏移。拖动预览旋转，滚轮缩放，使用「重置视角」和「线框」检查形状。模型保留源几何、底色与顶点色，预览采用工具光照；它不模拟世界曲率、风、天气、积雪或玩家碰撞。视觉绑定放在可选 `project.visuals` 字段，旧版草稿仍能读取；仅用户编辑后才产生视觉配置变更，游戏没有读取这些字段的入口。

游戏中的实体大多由 C++ 构建。工具专用导出器直接复用当前原几何函数：搭建件和建筑调用纯 C++ 网格入口，摆件和采集源在独立工具 GDExtension 中调用未修改的原函数，船模块从既有游戏 DLL 的合法参考布局截取。导出源文件与 DLL 的 SHA、构建工具、几何上下文记录在模型清单。建筑预览使用当前模板和平地，山墙有必要的相邻坡顶上下文；船模块的邻接墙面与栏杆取自注明的参考船布局。

采集用的树、灌丛、矿石与地面结壳属于「场景采集源」，不会默认冒充对应原料的库存实体，可在关联区临时查看。粮食颗粒、工艺品及一些基础材料目前没有独立的库存模型；粟、菽虽有田中植株，也不等于颗粒道具模型。缺失会说明来源状况，开发人员可显式绑定现有模型或导入自制模型。

「上传 OBJ 模型」将多边形几何导入工具本地库，支持三角面和凸共面多边形、负索引及法线，凹面、自交或非共面多边形须在建模软件中先三角化。单文件最多 5 MiB，不导入 MTL、贴图或动画。上传的库文件存放在 `workspace/assets/`，视觉配置的 JSON 导出只记录资产 ID；迁移自定义模型时还需备份该目录，不应只搬运草稿 JSON。

普通运行只需 Python，提交的模型快照可以直接预览。下面的模型重新导出脚本仍是可选的 Node 开发工具；日常编辑、模型上传和模型配置无需 Node。需要重新提取游戏源模型时运行：

```powershell
node tools/content-studio/model-export/export-models.mjs
```

导出器核对实际 Rider CMake 缓存、MSVC x64/Ninja/Debug、包含前缀和 Godot 路径，构建产物、日志、隔离 Godot 项目均位于工具忽略目录；不改写游戏 DLL、主项目构建缓存、资产或存档。失败记录退出码与日志，不能把旧快照当作重新导出成功。

## 保存、导入导出与冲突

持久化草稿保存在 `tools/content-studio/workspace/draft.json`，重置时的备份也写在这个工作目录，目录被 Git 忽略。文件封装包含版本、保存时间与校验指纹，不宜手工覆盖；请使用页面的 JSON 导入、导出。导出是可移动的完整草稿备份，可原样再导入；需要团队审阅时，把导出文件放到明确约定的位置另行提交，避免把本机工作区混进游戏内容提交。

保存采用版本检查。两个浏览器页面同时编辑时，较旧页面不能覆盖较新保存，服务返回 HTTP `409` 冲突；先导出旧页面中需要保留的内容，再读取最新草稿并合并。

草稿同时记录其源码基线的 hash。读取基线的 C++ 文件发生变化后，旧草稿会报告源码漂移，服务拒绝保存；不能把旧条目的整表替换误当作基于新源码的编辑。漂移的草稿仍可查看、导出和审阅差异。先导出保全草稿、核对当前源码和差异，再在「变更审阅 → 重置全部草稿」确认重置：工具先将旧文件备份为 `workspace/draft.backup.<UUID>.json`，随后立即保存基于当前源码的新草稿。要保留的编辑需逐项重新整理，旧导出文件不会被自动合并进新基线。

重置会放弃页面上尚未保存的编辑，因此重置前也要导出页面中的草稿保全。工具不自动重设旧草稿的基线，不自动合并源码变更。HTTP `409` 是冲突提示，不表示已有游戏内容或草稿被删除。

## 隔离与后续接入

内容草稿仍没有游戏加载入口。正式美术新增独立res://资源绑定与ArtSurface材质工厂，游戏运行不依赖工坊服务；`src/dev_manual.cpp` 的顶部注释记录制作与验收入口，`test_dev_manual` 核对文档一致性。

工具的内容草稿仍是独立管理与设计工作区，没有内容草稿的「应用到游戏」操作。正式美术由上方独立入口接入游戏。未来接入内容草稿时，仍须明确格式、迁移和旧存档规则，再执行相应验证，不得为生成器补造资源或地貌数据。

全项目的图片使用位置、现有缩略图与模型、分类需求、规格草案及风格待讨论项见 [美术图片资源需求清单](ART-ASSET-INVENTORY.md)，逐项快照见 [inventory.json](art-assets/inventory.json)。这两份资料为后续美术资产管理准备输入，当前尚未接入工具或游戏，也不构成可执行的生图队列。
